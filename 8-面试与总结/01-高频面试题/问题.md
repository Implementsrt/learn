# 讨论问题汇总

---

## 问题1：SATB队列处理中C和E的处理逻辑为什么不一样 / "扁平"和"深度遍历"是什么意思

### 关于C和E的处理逻辑

C 和 E 的处理逻辑**完全相同**，只是文字描述上做了简写：

| 步骤 | C | E |
|------|---|---|
| 取出 | ✅ | ✅ |
| 判断白色？ | ✅ 是白色 | ✅ 是白色 |
| 标记为灰色 | ✅ | ✅（"标记"就是标记为灰色） |
| 扫描它的引用 | ✅ | ✅（"扫描"就是扫描它的引用） |

E 那行只是偷懒缩写了，没有本质区别。D 才是真正不同的——因为 D 已经是黑色（已扫描完毕），所以**跳过**。

### 关于"扁平"（Flat）

指 SATB（Snapshot At The Beginning，原始快照）队列的结构是一个**一维线性列表**，里面存的是一个个**旧引用值**（被覆盖前的指针）。

处理方式：每个条目**独立**处理，处理完就下一个，不需要从某个条目出发再递归地追踪下去。就像遍历一个数组，**广度浅、没有嵌套**，所以叫"扁平"。

### 关于"深度遍历"（Deep Traversal）

指 CMS（Concurrent Mark Sweep，并发标记清除）增量更新的处理方式。CMS 用的是**脏卡（Dirty Card）** 机制——只知道"这块内存区域里有引用被改了"，但不知道具体改了哪个引用。从一个脏对象出发，要**递归追踪**它引用的所有对象，以及那些对象引用的对象……像一棵树，一层一层往深处走。

### 对比

| | SATB（G1） | 增量更新（CMS） |
|---|---|---|
| **队列存的是什么** | 旧引用值（精确的指针） | 脏卡（粗粒度的内存区域） |
| **处理方式** | 逐个取出 → 标记 → 下一个 | 扫描脏卡区域 → 找到对象 → **递归追踪引用链** |
| **深度** | 1 层（扁平） | N 层（不确定） |
| **Remark STW 时间** | 短且稳定 | 长且波动大 |

## 问题2：为什么白色的C要标记为灰色而不是回收 / 增量更新记录的到底是"A对象"还是"脏卡"

### 为什么白色的C要标记为灰色

SATB 队列里存的是**被覆盖前的旧引用值**。C 出现在队列里，意味着在并发标记开始时，C 是被某个对象引用着的（是存活的）。SATB 的核心原则：**以并发标记开始那一刻的对象图快照为准——那一刻活着的对象，这轮 GC 就不回收。**

C 确实可能已经是垃圾了，但 SATB 宁可这轮"放过"它（浮动垃圾），也不能误杀。C 会在**下一轮**并发标记中被识别为白色并回收。

### 增量更新记录的是"A对象"还是"脏卡"

两者都有，是**两层机制**：

- **第一层**：写屏障把 A 所在的卡页标记为"脏"（粗粒度，精确到 512 字节区域）
- **第二层**：Remark 时扫描脏卡区域 → 找到区域内所有对象 → 从这些引用出发递归追踪

**一句话：逻辑上是"记录 A"，实现上是"标脏 A 所在的卡页"，Remark 时要从卡页反查 A 再递归追踪。**

## 问题3：浮动垃圾是什么意思

**浮动垃圾（Floating Garbage）** 指的是在一轮 GC 并发标记过程中**实际已经没有任何引用指向、本应被回收，但因为 GC 算法的保守策略而在这一轮中"逃过"回收的对象**。

以 G1 的 SATB 为例：并发标记开始时 A.field → C（C 是活的），并发标记过程中 A.field = null（C 没人引用了），但 SATB 规则是"标记开始时活着就不回收"→ C 就是浮动垃圾，下一轮才会被回收。

- **通常无害**——只是多占一轮的内存
- **极端情况有害**——浮动垃圾量大可能导致堆空间不足，间接触发 Full GC

---

## 问题4：CMS和G1浮动垃圾产生的具体阶段

### CMS

主要来源是**第四阶段（并发清除）**：清除阶段和应用线程并发运行，应用线程在此期间新产生的垃圾无法被本轮清除。第二阶段（并发标记）也会产生少量。

### G1

浮动垃圾不是 Remark 阶段"产生"的，而是 **SATB 机制从并发标记开始就决定了的**：

| 时间点 | 发生了什么 |
|---|---|
| **并发标记开始** | SATB 拍下快照：此刻活着的对象都保留 |
| **并发标记过程中** | 应用线程断开引用，写屏障把旧引用放入 SATB 队列 |
| **Remark 阶段** | 处理 SATB 队列，把旧引用标记为存活——"宁放过不杀错"的执行点 |

---

## 问题5：SATB是什么的缩写

**SATB = Snapshot At The Beginning**，中文译为"原始快照"。在并发标记开始的那一刻，对整个对象引用关系拍一个逻辑上的"快照"，后续标记以这个快照为准来判断对象是否存活。

---

## 问题6：LSN是什么缩写

**LSN = Log Sequence Number**，中文译为"日志序列号"。是 MySQL InnoDB 中用来标识 redo log（重做日志）写入位置的一个**单调递增的编号**。用于追踪当前 redo log 写到了哪里、数据页最后一次被刷盘时的日志位置、崩溃恢复时从哪个位置开始重放日志。

---

## 问题7：LSN相当于MongoDB的ObjectId对吗

不对。LSN 标识的是 redo log 的写入位置（字节偏移量），用于崩溃恢复和数据页同步追踪；MongoDB ObjectId 标识的是一条文档的唯一标识，用于查询和索引。LSN 像书签（标记读到哪了），ObjectId 像身份证号（标识你是谁）。

---

## 问题8：LSN和ConcurrentHashMap的modCount的关系

`modCount`（modification count，修改计数器）和 LSN 都是递增数字，但作用完全不同：

- **LSN 是位置标记**：redo log 写到了第几个字节，用于崩溃恢复定位
- **modCount 是变化检测器**：集合被结构性修改了几次，用于 fast-fail 机制——迭代过程中检测到变化就抛 `ConcurrentModificationException`

如果要给 LSN 找类比，更像 **MySQL binlog 的 position**——都是日志中的字节位置标记。

---

## 问题9：LSN在Xtrabackup中识别修改过的页

对，这是 LSN 的一个重要应用场景。

**Xtrabackup**（Percona 开发的 MySQL 热备份工具）在做**增量备份**时，核心逻辑就是靠 LSN 来识别哪些数据页被修改过：

1. **全量备份时**：记录下当时的 LSN 值（比如 LSN = 10000）
2. **增量备份时**：扫描所有 InnoDB 数据页，每个数据页头部都记录了它最后一次被修改时的 LSN
3. **对比**：页 LSN > 上次备份 LSN → 被修改过 → 备份；否则跳过

```
数据页 A：LSN = 12000 > 10000 → 改过 → 备份 ✅
数据页 B：LSN = 8000  ≤ 10000 → 没改 → 跳过 ❌
数据页 C：LSN = 15000 > 10000 → 改过 → 备份 ✅
```

LSN 的作用总结：

| 作用 | 说明 |
|---|---|
| **崩溃恢复** | 确定从 redo log 的哪个位置开始重放 |
| **数据页同步追踪** | 判断内存中的脏页是否已经刷盘 |
| **增量备份（Xtrabackup）** | 对比页 LSN 和上次备份 LSN，只备份增量部分 |

## 问题10：binlog的偏移量是全局还是每个文件独立

**每个 binlog 文件独立计算。**

每个文件内部的 position（偏移量）都是从 4 开始的（前 4 个字节是 magic number 头部标识）。定位一个 binlog 事件需要**两个值**：文件名 + 偏移量。

```sql
CHANGE MASTER TO
  MASTER_LOG_FILE = 'mysql-bin.000003',
  MASTER_LOG_POS = 1024;
```

### 和 GTID（Global Transaction ID，全局事务标识）的对比

| | file + position | GTID |
|---|---|---|
| **作用域** | 每个文件独立 | **全局唯一** |
| **格式** | `mysql-bin.000003:1024` | `server_uuid:transaction_id` |
| **切换主库** | 需要手动找对应 file + position，容易出错 | 自动定位 |
| **推荐程度** | 传统方式，MySQL 5.6 之前唯一选择 | MySQL 5.6+ 推荐 |

## 问题11：CMS对CPU敏感，G1也有这个问题吗

对，G1 的并发标记阶段也会占用 CPU，**两者都有这个问题**。但 G1 比 CMS 做了改进。

| 因素 | CMS | G1 |
|---|---|---|
| **并发标记占 CPU** | ✅ 有 | ✅ 也有 |
| **并发清除也占 CPU** | ✅ 第四阶段并发清除持续占 CPU | ⚠️ 没有并发清除阶段，回收在 STW 的筛选回收阶段完成 |
| **Remark 开销** | ❌ 大——重新扫描脏卡 + 深度遍历 | ✅ 小——处理扁平的 SATB 队列 |
| **低核数影响** | ❌ 严重——CMS 设计年代很多机器只有 2~4 核 | ✅ 较轻——G1 设计年代服务器普遍 8 核以上 |

关键区别：CMS 的并发阶段更长（并发标记 + 并发清除），持续占 CPU 时间窗口更大。G1 把回收工作放在 STW 的筛选回收阶段，STW 期间所有 CPU 都在干 GC，干完立刻还给业务。

## 问题12：TLAB中的对象是否不在堆上创建

不对。TLAB（Thread Local Allocation Buffer，线程本地分配缓冲区）**就是堆内存的一部分**，对象从一开始就是在堆上创建的。

```
堆内存
└── 新生代
    └── Eden 区（整块连续内存）
        ├── 线程 A 的 TLAB（Eden 区中划出的一小段地址范围）
        ├── 线程 B 的 TLAB（另一小段地址范围）
        └── 线程 C 的 TLAB（又一小段地址范围）
```

- TLAB **在 Eden 区里面**，是 Eden 内存的一个子区间
- 对象**从创建那一刻起就在 Eden 区（堆上）**，不存在"先在外面创建再合并"
- TLAB 只是避免多线程分配时的锁竞争，不改变分配位置
- 类比：大停车场（Eden）给每个入口分了专属车道（TLAB），车停进去就已经在停车场里了

---

## 问题13：TLAB作为"对象不在堆上分配"的例子是否错误

对，TLAB 作为"对象不一定在堆上分配"的例子是**错的**。TLAB 分配的对象就是在堆上（Eden 区），只是分配方式做了优化。

正确的两个例子：

| 优化 | 分配位置 | 说明 |
|---|---|---|
| **① 逃逸分析 + 栈上分配** | **栈** | 对象没有逃逸出方法 → JIT 直接在栈帧上分配 |
| **② 逃逸分析 + 标量替换** | **不分配对象** | JIT 把对象拆成基本类型局部变量，连对象本身都不创建 |

---

## 问题14：逃逸分析+栈上分配只能是JIT不能是解释器吗

对，**只有 JIT（Just-In-Time Compiler，即时编译器）能做，解释器做不了。**

| | 解释器 | JIT 编译器 |
|---|---|---|
| **工作粒度** | 逐条字节码指令执行 | 对整个方法做全局分析后编译 |
| **能否做逃逸分析** | ❌ 只看当前一条指令 | ✅ 编译时分析整个方法的引用关系 |
| **能否栈上分配** | ❌ 字节码 `new` 语义就是堆上分配，解释器忠实执行 | ✅ 生成的机器码直接在栈上分配 |
| **能否标量替换** | ❌ 不会改变字节码语义 | ✅ 把对象拆成局部变量 |

核心区别：**解释器是"忠实翻译"，JIT 是"重新创作"**。没被 JIT 编译的方法，对象永远在堆上分配。

---

## 问题15：即时编译器和解释器的关系是什么

JIT 和解释器是 JVM 中执行字节码的**两种方式**，采用**混合模式（Mixed Mode）**协同工作：

```
程序启动 → 所有方法先用解释器执行（启动快）
  → JVM 统计每个方法的调用次数 + 循环次数
  → 达到阈值（"热点"）→ 触发 JIT 编译
  → 编译完成后直接执行机器码（不再走解释器）
```

| | 解释器 | JIT 编译器 |
|---|---|---|
| **启动速度** | ✅ 快 | ❌ 需要编译时间 |
| **运行速度** | ❌ 每次都要翻译 | ✅ 编译一次后续直接执行机器码 |
| **类比** | 同声传译 | 提前翻译整本书 |

HotSpot JVM 有两个 JIT：C1（轻量优化，快）和 C2（深度优化，慢）。现代 JVM 用**分层编译**：解释执行 → C1 → C2。

**一句话：解释器保证启动快，JIT 保证运行快，两者分工协作。**

## 问题16：频繁Young GC导致接口抖动，接口抖动是什么意思

**接口抖动**指同一个接口的**响应时间不稳定**——间歇性地突然变慢，然后又恢复正常。

```
正常：  2ms, 3ms, 2ms, 3ms, 2ms
抖动：  2ms, 3ms, 150ms, 2ms, 3ms, 200ms, 2ms
                  ↑                ↑
               突然变慢          又突然变慢
```

Young GC 是 STW 的，频繁 Young GC → 用户请求频繁撞上 GC 停顿 → 响应时间出现毛刺/尖峰。

常见原因和解决：

| 原因 | 解决 |
|---|---|
| Eden 区太小 → 频繁触发 | 增大 Eden（`-Xmn` 或 `G1NewSizePercent`） |
| 对象分配速率太高 | 优化代码减少临时对象 |
| 单次 Young GC 耗时长 | 排查大量对象不合理存活到 Survivor |

## 问题17：G1MixedGCLiveThresholdPercent参数是什么意思

`G1MixedGCLiveThresholdPercent=85`（混合GC存活率阈值）：**老年代 Region 中存活对象占比超过 85% 的，不会被选入回收集合。**

原因：Mixed GC 用标记-复制算法，存活率 90% 的 Region 要复制 90% 的对象，只释放 10% 空间——干活多、收益少。G1 优先回收垃圾最多的 Region（Garbage First），这个参数划定了性价比底线。

| 调整方向 | 效果 |
|---|---|
| **调大**（如 90%） | 更多 Region 被纳入回收 → 回收更彻底，停顿更长 |
| **调小**（如 65%） | 只回收垃圾率特别高的 → 每轮更快，但回收不彻底 |

## 问题18：G1HeapRegionSize设置8M时Region数量是多少

显式设置 `-XX:G1HeapRegionSize=8m`，堆 8192MB → **1024 个 8MB 的 Region**。

`G1HeapRegionSize` 是**强制参数**，设成 8MB 就用 8MB。只有**不设置**时 JVM 才自动计算：

```
Region 大小 = 堆大小 ÷ 2048（目标 Region 数量）
8192MB ÷ 2048 = 4MB → 自动选择 4MB
```

| 场景 | Region 大小 | Region 数量 |
|---|---|---|
| 不设置，堆 8192MB | 4MB（自动） | 2048 个 |
| 设置 8m，堆 8192MB | 8MB（指定） | 1024 个 |

更大 Region 的影响：Humongous 阈值变大（减少大对象问题），但 Region 数量变少（调度粒度变粗）。

---

## 问题19：Humongous是什么

Humongous 不是缩写，是英文单词，意思是"巨大的"。在 G1 GC 中是专有术语：

**Humongous Object（巨大对象）**：大小超过单个 Region 容量 50% 的对象。例如 Region 8MB → 对象超过 4MB → Humongous。

存放 Humongous Object 的 Region 叫 **Humongous Region**，特殊规则：

1. **直接分配在老年代**，不经过 Eden → Survivor 的晋升流程
2. **必须占用连续的 Region**——10MB 对象，8MB Region → 需要连续 2 个 Region
3. **剩余空间浪费**——2 个 Region = 16MB，对象只用 10MB，剩下 6MB 不能给其他对象用

对性能的影响：

| 问题 | 原因 |
|---|---|
| **内存浪费** | 尾部 Region 剩余空间无法利用 |
| **分配慢** | 需要找到连续的空闲 Region |
| **回收时机特殊** | JDK 8u40 之前只在 Full GC 时回收；之后优化为并发标记 Cleanup 阶段也可回收 |
| **可能触发 Full GC** | 找不到足够连续空闲 Region → 直接 Full GC |

优化方式：增大 Region 大小（`-XX:G1HeapRegionSize`）或从代码层面用流式读取避免产生大对象。

## 问题20：G1MixedGCCountTarget是硬性值吗

不是硬性值，是**软目标**。

`G1MixedGCCountTarget=8`（混合GC目标次数，默认值）的意思是：G1 **尽量**在 8 轮 Mixed GC 内回收完并发标记周期中标记出的所有待回收老年代 Region。

实际轮数可能少于 8 轮：

| 情况 | 原因 |
|---|---|
| **提前停止** | 剩余垃圾低于 `G1HeapWastePercent`（堆垃圾浪费比例，默认 5%）→ 不值得再收 |
| **被 Young GC 打断** | Young GC 已释放足够空间 |
| **本来就不多** | 待回收 Region 几轮就收完了 |

它影响的是"每轮收多少"：

```
待回收 160 个 Region / G1MixedGCCountTarget=8 = 每轮约 20 个
```

这个 20 也不精确——G1 还结合 `MaxGCPauseMillis`（最大GC停顿时间目标）和 `G1OldCSetRegionThresholdPercent`（老年代CSet占比上限）做最终决定。

---

## 问题21：G1HeapWastePercent是什么

`G1HeapWastePercent`（堆垃圾浪费比例，默认 5%）控制：**Mixed GC 什么时候提前停止。**

> 当整个堆中可回收的垃圾总量低于堆大小的 `G1HeapWastePercent` 时，停止本轮 Mixed GC 周期。

```
堆 8GB，G1HeapWastePercent=5%，阈值 = 400MB

Mixed GC 第 1 轮：剩余可回收 1.5GB → > 400MB → 继续
Mixed GC 第 2 轮：剩余可回收 1.0GB → > 400MB → 继续
Mixed GC 第 3 轮：剩余可回收 600MB → > 400MB → 继续
Mixed GC 第 4 轮：剩余可回收 350MB → < 400MB → 停止！
```

四个参数配合决定 Mixed GC 行为：

| 参数 | 控制什么 |
|---|---|
| `G1MixedGCCountTarget` | 每轮收多少个 Region |
| `G1MixedGCLiveThresholdPercent` | 哪些 Region 值得收 |
| **`G1HeapWastePercent`** | **什么时候停止收** |
| `MaxGCPauseMillis` | 每轮 STW 时间上限 |

## 问题22：Survivor什么时候会回收

Survivor Region 在 **Young GC** 时被回收，和 Eden Region 一起处理。没有单独的 Survivor GC。

每次 Young GC 范围：**所有 Eden Region + 所有 Survivor Region**

```
Young GC 触发：
  扫描：所有 Eden + 所有 Survivor（上一轮的）
  存活对象：
    年龄 < 晋升阈值 → 复制到新的 Survivor Region
    年龄 ≥ 晋升阈值 → 复制到 Old Region（晋升）
  原来的 Eden + Survivor → 清空 → 变成 Free
```

| GC 类型 | 是否回收 Survivor |
|---|---|
| **Young GC** | ✅ 每次都回收 |
| **Mixed GC** | ✅ 包含完整 Young GC |
| **Full GC** | ✅ 回收整个堆 |

每轮都是：**上一轮的 Survivor 被清空回收，新的 Survivor 被创建。** 在 G1 中，Survivor 不是固定的两块区域，而是每轮 GC 时从 Free Region 中选取新的 Region 来充当。

---

## 问题23：G1每种回收都是使用的什么算法

| GC 类型 | 算法 | 说明 |
|---|---|---|
| **Young GC** | 标记-复制 | 存活对象复制到新 Region → 清空原 Region |
| **Mixed GC** | 标记-复制 | 同 Young GC，选中的 Region 中存活对象复制到新 Region |
| **Full GC** | 标记-整理 | 全堆范围，存活对象向一端移动压缩 |

为什么 Young GC 和 Mixed GC 用标记-复制：没有碎片，回收速度取决于存活对象数量（少就快）。

为什么 Full GC 用标记-整理：Full GC 是空间严重不足时触发的，没有足够 Free Region 做复制目标，标记-整理可以在原地压缩。

**有空间腾挪时用标记-复制（快、无碎片），没空间时退化为标记-整理（慢、但能原地压缩）。**

---

## 问题24：Eden满了算的是Eden还是Eden+Survivor

**只算 Eden，不算 Survivor。**

G1 维护一个当前 Eden Region 数量上限（动态计算）。当已分配的 Eden Region 数量达到上限时触发 Young GC。Survivor 不参与判定。

原因：触发 Young GC 的根本原因是**新对象没地方放了**，而新对象只往 Eden 放。Survivor 是上一轮 GC 留下的，不会持续增长。

## 问题25：Eden Region数量上限有哪些相关参数

### 直接控制

| 参数 | 中文含义 | 作用 |
|---|---|---|
| `G1NewSizePercent`（新生代最小占比，默认 5%） | Eden + Survivor 不低于堆的 5% |
| `G1MaxNewSizePercent`（新生代最大占比，默认 60%） | Eden + Survivor 不超过堆的 60% |

### 间接影响

| 参数 | 中文含义 | 如何影响 |
|---|---|---|
| `MaxGCPauseMillis`（最大GC停顿时间目标，默认 200ms） | G1 根据历史数据预估 Eden 多大能让 STW 不超标。目标设越小 → Eden 被压越小 → GC 越频繁 |
| `G1HeapRegionSize`（Region大小） | Region 越大，同样数量 Region 意味着 Eden 越大 |

G1 在 `G1NewSizePercent` 和 `G1MaxNewSizePercent` 的上下界内，根据 `MaxGCPauseMillis` 和历史 GC 数据**动态调整** Eden 大小（反馈循环）。

## 问题26：新生代Region数量是否会突破G1MaxNewSizePercent的60%

**不会突破。`G1MaxNewSizePercent` 是硬上限。**

```
堆 = 2048MB，Region = 1MB → 共 2048 个 Region
G1MaxNewSizePercent = 60%
新生代 Region 硬上限 = 2048 × 60% = 1228 个
```

不管 `MaxGCPauseMillis` 怎么设，新生代 Region 永远不会超过 1228 个。反过来也一样，不会低于 `G1NewSizePercent` 的下限。

```
参数优先级：
  硬约束（绝对不突破）：G1NewSizePercent（下限）、G1MaxNewSizePercent（上限）
  软目标（在硬约束范围内调整）：MaxGCPauseMillis
```

**`G1NewSizePercent` 和 `G1MaxNewSizePercent` 是铁栅栏，`MaxGCPauseMillis` 只能在栅栏内活动。**

## 问题27：贪心算法是什么

**贪心算法（Greedy Algorithm）** 是一种在每一步都选择**当前看起来最优的选择**，希望最终得到全局最优解的算法策略。核心：**每步做局部最优选择，不回头，不考虑未来。**

经典例子——找零钱（面额 25、10、5、1 分，凑 41 分）：

```
第 1 步：41 ≥ 25 → 用 25 → 剩 16
第 2 步：16 ≥ 10 → 用 10 → 剩 6
第 3 步：6 ≥ 5  → 用 5  → 剩 1
第 4 步：1 ≥ 1  → 用 1  → 剩 0
结果：4 枚硬币 ✅
```

但换面额就可能出错（面额 11、5、1，凑 15）：贪心选 11+1+1+1+1=5 枚 ❌，最优是 5+5+5=3 枚 ✅。

### 贪心 vs 动态规划（DP，Dynamic Programming）

| | 贪心 | 动态规划 |
|---|---|---|
| **决策方式** | 每步选当前最优，不回头 | 考虑所有子问题，选全局最优 |
| **时间复杂度** | 通常更快 | 通常更慢但保证最优 |
| **适用条件** | 局部最优 = 全局最优 | 有重叠子问题 + 最优子结构 |

常见应用：活动选择、Huffman 编码、Dijkstra 最短路径、Kruskal/Prim 最小生成树。

| 看什么 | 健康值 |

| 堆回收效率 | GC 后堆占用持续上升不降 → 可能内存泄漏 |

## 问题29：Card Table存储单位大小计算

### 逐步计算

```
堆大小 = 4GB = 4,294,967,296 Bytes
每个 Card = 512 Bytes

Card 数量 = 4,294,967,296 / 512 = 8,388,608 个 ≈ 8M 个
（这里 M = 百万，即 Mega，不是 MB）

Card Table 每个条目 = 1 Byte（一个字节，标记 Clean 或 Dirty）

Card Table 大小 = 8,388,608 × 1 Byte = 8,388,608 Bytes = 8 MB
```

### 汇总

| 项目 | 大小 |
|---|---|
| 堆大小 | 4 GB = 4,294,967,296 Bytes |
| 每个 Card | 512 Bytes |
| Card 数量 | 8,388,608 个（≈ 8M 个） |
| Card Table 每条目 | 1 Byte |
| **Card Table 总大小** | **8 MB** |

Card Table 占堆大小的比例 = 8MB / 4GB ≈ 0.2%（固定比例 1:512）。

## 问题30：CMS通过卡表和G1通过SATB处理并发标记的对比

### CMS（增量更新）

```
并发标记期间：A.field 从 C 改成 D
→ 写屏障把 A 所在的 Card 标记为脏
→ Remark：扫描脏卡 → 找到 A → 从 A 出发重新遍历引用链 → 标记 D 及其子图
→ 关注的是"A 现在指向谁"（新引用）
```

### G1（SATB）

```
并发标记期间：A.field 从 C 改成 D
→ 写屏障把旧值 C 放入 SATB 队列
→ Remark：取出 C → 标记为灰色 → 扫描 C 的引用 → 最终变黑
→ 关注的是"C 之前被引用过"（旧引用）
```

注意：C 先标记为灰色（存活，待扫描），扫描完引用后才变黑色（扫描完成）。过程是**白 → 灰 → 黑**，不是直接变黑。

另外，G1 **也有卡表**，但不用于并发标记——G1 的卡表配合 RSet（Remembered Set，记忆集）用于跨 Region 引用追踪。并发标记期间的引用变化由 SATB 队列处理。

**一句话：CMS 追踪"谁被改了"（A），G1 追踪"谁被丢了"（C）。**

## 问题31：CMS和G1卡表的用途区别

### CMS 的卡表——两个用途，两个使用者

| 用途 | 谁在用 | 什么时候 |
|---|---|---|
| **跨代引用** | **ParNew**（新生代收集器） | Minor GC 时，通过脏卡找到老年代指向新生代的引用 |
| **增量更新** | **CMS**（老年代收集器） | Remark 时，重扫脏卡处理并发标记期间的引用变化 |

CMS 和 ParNew 是搭配使用的，**共享同一张卡表**。

### G1 的卡表——只有一个用途

| 用途 | 说明 |
|---|---|
| **配合 RSet** | 跨 Region 引用 → 卡表标脏 → 后台 Refinement 线程异步更新 RSet → Card 重置 Clean |
| ~~并发标记~~ | ❌ 不用于并发标记——用 SATB 队列代替 |

### 总结

CMS 和 G1 的卡表都用于跨代/跨区引用追踪。区别在于并发标记这件事上：CMS 复用卡表做增量更新，G1 不复用卡表而是单独用 SATB 队列。

## 问题32：CMS卡表跟跨代有关？CMS不是只作用在老年代吗

CMS 确实**只负责回收老年代**，但卡表的跨代引用追踪**不是 CMS 自己用的，而是给 ParNew（Minor GC）用的**。

```
老年代对象 A 引用了新生代对象 B（A.field = B）

ParNew 做 Minor GC 时只扫描新生代
→ 但 B 被老年代的 A 引用着 → B 是存活的
→ 如果不知道 A 的存在，就会误杀 B

卡表记录了"老年代哪些区域有指向新生代的引用"
→ ParNew 扫描脏卡 → 找到 A → 知道 B 还活着
```

CMS 和 ParNew 搭配使用，共享同一张卡表。卡表的跨代引用功能是 ParNew 用的，增量更新功能是 CMS 用的。

**一句话：卡表是共享的基础设施，ParNew 用它做跨代引用追踪，CMS 复用它做增量更新。**

## 问题33：G1写屏障比CMS重的原因

方向对，但不只是多了 SATB 一项。G1 写屏障同时要做**三件事**：

### CMS 写屏障做的事

每次引用修改时（如 `A.field = B`）：

```
① 标脏卡（把 A 所在的 Card 标记为 Dirty）
```

就这一步，非常轻量。

### G1 写屏障做的事

每次引用修改时（如 `A.field = B`，旧值是 C）：

```
① SATB 队列：把旧值 C 放入当前线程的 SATB 队列（用于并发标记）
② 卡表标脏：把 A 所在的 Card 标记为 Dirty
③ Dirty Card Queue（脏卡队列）：把脏卡信息放入队列，由后台 Refinement 线程异步更新 RSet
```

### 对比

| | CMS | G1 |
|---|---|---|
| **① SATB 记录旧引用** | ❌ 不需要 | ✅ 旧值入 SATB 队列 |
| **② 卡表标脏** | ✅ | ✅ |
| **③ 维护 RSet** | ❌ 不需要（没有 RSet） | ✅ 脏卡入队列 → 后台线程异步更新 RSet |

CMS 不需要 RSet 是因为传统分代模型只有老年代 → 新生代一个方向的跨代引用，一张卡表就够了。G1 有上千个 Region，任意两个之间都可能有引用，需要 RSet 精确追踪。

**G1 写屏障重的主要原因是 RSet 维护（最大额外开销），SATB 入队是次要原因。**

---

## 问题34：G1和CMS卡表清理时机的对比

### G1 的卡表清理

```
写屏障标脏卡 → 脏卡入队 → 后台 Refinement（精炼）线程异步处理
→ 更新目标 Region 的 RSet → 把卡标记为 Clean
```

G1 的脏卡是**后台线程异步、持续地清理**的，不用等到 GC 暂停时。

### CMS 的卡表清理

CMS 共享的卡表有两个用途，清理时机不同：

**用途一：跨代引用（ParNew 使用）**

```
老年代对象引用修改 → 标脏
→ ParNew Minor GC 时：扫描所有脏卡 → 找跨代引用 → 扫描完毕后标为 Clean
```

清理时机：**Minor GC 结束时**。

**用途二：增量更新（CMS 并发标记使用）**

```
并发标记期间引用修改 → 标脏
→ Remark 阶段：扫描所有脏卡 → 重新遍历引用链 → 扫描完毕后标为 Clean
```

清理时机：**Remark 阶段处理完脏卡后**。

### 对比

| | CMS | G1 |
|---|---|---|
| **脏卡清理时机** | GC 暂停时同步清理（攒到 GC 时一起扫） | 后台线程异步持续清理 |
| **影响** | 脏卡越多 → GC 暂停扫描时间越长 | 脏卡被持续消化，GC 暂停时剩余脏卡少 |

G1 用后台 Refinement 线程持续消化脏卡，是因为上千个 Region 产生的跨区引用远多于 CMS 的跨代引用，攒到 GC 时才处理会导致暂停时间飙高。

## 问题35：CMS卡表用于跨代回收的具体使用方式

卡表本身只标记"哪个 Card 脏了"，但通过以下流程加速跨代引用查找：

### 完整流程

**第一步：运行时——维护脏标记**

```
OldObj.field = YoungObj;   // 老年代引用新生代
写屏障触发 → OldObj 所在的 Card 标记为 Dirty
```

注意：**任何引用修改都标脏**，不区分是否跨代。

**第二步：Minor GC 时——扫描脏卡**

```
遍历卡表（只看老年代范围）→ 找到所有 Dirty 的 Card
  → 扫描每个脏 Card 的 512 Bytes 区域
    → 找出所有对象的引用字段
      → 如果引用指向新生代 → 把被引用对象标记为存活
```

**第三步：扫描完——清除脏标记**

处理完所有脏卡 → 重置为 Clean。

### 为什么比扫描整个老年代快

| 方式 | 扫描范围 |
|---|---|
| 没有卡表 | 整个老年代所有对象的所有引用字段（可能几 GB） |
| 有卡表 | 只扫描标记为 Dirty 的 Card（每个 512 Bytes） |

老年代大部分对象是"安静"的——引用很久没变 → Card 是 Clean → 直接跳过。

卡表的局限：只知道"这 512B 区域有变化"，不知道具体哪个对象、是否跨代——所以是"粗粒度"过滤。但即使有额外扫描，也远比遍历整个老年代快。

## 问题36：只扫描脏卡能否找出所有老年代对新生代的引用

**只扫描脏卡确实不能直接找出所有跨代引用**——卡表只在引用被修改时标脏，但有些跨代引用从来没被修改过（Card 早就被清为 Clean 了）。

但实际上**不会遗漏**，原因：

### 新生代对象每次 GC 都会被复制（地址变化）

```
① A（老年代）.field = B（新生代）→ A 的 Card 标脏

② Minor GC：扫描脏卡 → 发现 A → B 的引用
   → B 存活 → B 被复制到新 Survivor（地址变了）
   → GC 更新 A.field 指向 B 的新地址
   → A 的 Card 重新标脏（因为 A 的引用被 GC 更新了）

③ 下次 Minor GC：A 的 Card 还是脏的 → 再次扫描 → 还能找到跨代引用
```

**只要 B 还在新生代，每次 Minor GC 都会复制 B → 更新 A 的引用 → A 的 Card 重新标脏 → 下次还能扫到。**

其他情况：

| 场景 | 能否找到 | 原因 |
|---|---|---|
| 老年代**新建/修改**了对新生代的引用 | ✅ | 引用修改触发写屏障 → 标脏 |
| 老年代引用**很久没变**但指向新生代 | ✅ | 新生代对象每次 GC 被复制 → GC 更新引用 → 重新标脏 |
| B 晋升到老年代后 | 不需要找 | 不再是跨代引用 |

**一句话：新生代对象每次 GC 都被复制到新地址 → GC 必须更新所有指向它的引用 → 引用更新触发标脏 → 脏卡机制能持续追踪所有跨代引用，不会遗漏。**

## 问题37：G1的SATB好像不能解决黑色对象引用新对象的情况

### 场景

```
并发标记期间：
  A 已经被标记为黑色（自身和所有引用都扫描完了）
  应用线程执行：D = new Object(); A.field = D;

SATB Pre-Write Barrier 记录的是旧值（null 或 C），对新创建的 D 没有直接保护。
```

### D 是怎么被保护的：TAMS（Top At Mark Start，标记起始顶部指针）

每个 Region 维护一个 TAMS 指针 = 并发标记开始时该 Region 的分配位置（"水位线"）。

```
┌────────────────────────────────────┐
│  Region                            │
│  [旧对象][旧对象][旧对象]│TAMS│[D][E][F]  │
│  ←── 标记开始前分配的 ──→│    │←── 标记期间新分配的 ──→
└────────────────────────────────────┘
```

**规则：TAMS 之上（标记开始后新分配的对象）一律视为存活，不需要标记。**

D 是并发标记期间 new 出来的 → 分配位置在 TAMS 之上 → G1 自动认为 D 存活 → 不会被回收。

### G1 并发标记不漏标的三道防线

| 防线 | 保护什么 | 机制 |
|---|---|---|
| **① SATB Pre-Write Barrier** | 被覆盖的旧引用（如 C） | 旧值入 SATB 队列 → Remark 时标记存活 |
| **② TAMS 指针** | 并发标记期间新分配的对象（如 D） | TAMS 之上一律存活 |
| **③ 黑色对象引用新对象** | 就是这个场景 | 由 TAMS 兜底——D 是新对象，已被 TAMS 保护 |

代价同样是浮动垃圾：并发标记期间 new 的 D 如果很快变成垃圾，这轮也不会收它。

## 问题38：SATB为什么叫原始快照，跟快照没关系

SATB **确实没有拍一张真正的快照**，"原始快照"是**逻辑概念**，不是物理操作。

### "快照"是目标保证，不是实现方式

SATB 的承诺：**并发标记开始那一刻（T0），所有可达的对象，这轮 GC 都不会回收。** 这等价于：如果你能在 T0 瞬间冻结整个对象图拍一张照片，照片里能看到的对象都保留。

| | 真正拍快照（理想方案） | SATB 的实际做法 |
|---|---|---|
| **做法** | T0 复制一份整个对象图 | T0 什么都不做 → 引用被删除时记录旧值 |
| **效果** | T0 的对象图被完整保留 | T0 的对象图被**等价保留** |
| **开销** | 不可接受（复制整个堆） | 很小（只在引用变化时记一笔） |

### 为什么等价

- 如果从 T0 到标记结束，所有引用都没变 → 正常遍历就能找到所有对象 → 不需要额外处理
- 如果有引用被删除 → 写屏障记录旧值 → 补上"断裂的边" → 还是等价

### "At The Beginning"强调的是参考时间点

| | SATB（原始快照） | 增量更新（CMS） |
|---|---|---|
| **参考点** | 标记开始时的状态 | 标记结束时的最新状态 |
| **关注** | "开始时活着的" → 保留 | "结束时活着的" → 精确找到 |

**一句话："快照"是目标（保证 T0 的存活集合不丢），不是实现（没有真的复制数据）。写屏障是用最小代价达到这个目标的技巧。**

---

## 问题39：MVCC也不复制数据，是通过ReadView和undo log版本链

对，但原始提问中说的是"redo log 版本链"，这里纠正：**版本链在 undo log（回滚日志）里，不是 redo log（重做日志）**。

| | redo log（重做日志） | undo log（回滚日志） |
|---|---|---|
| **记录什么** | "做了什么改动"（物理修改） | "改之前是什么"（旧版本数据） |
| **用途** | 崩溃恢复 | ① 事务回滚 ② **MVCC 读取历史版本** |

MVCC 的正确描述：

```
① 修改数据时：旧版本写入 undo log → 新版本写入数据页 → roll_pointer 指向旧版本
  形成版本链：当前版本 → undo log 旧版本1 → undo log 旧版本2 → ...

② 读数据时：生成 ReadView（读视图）→ 沿版本链往回找 → 找到第一个"可见"的版本
```

## 问题40：SATB和MVCC都不复制数据的对比

之前说"不像 MVCC 那样复制数据"是不准确的。MVCC 也不复制数据。

| | SATB | MVCC |
|---|---|---|
| **"快照"是什么** | T0 时刻的对象可达性 | 事务开始时的数据状态 |
| **物理复制？** | ❌ 没有 | ❌ 没有 |
| **怎么实现等价效果** | 写屏障记录被删除的旧引用 | undo log 保留旧版本 + ReadView 判断可见性 |
| **代价** | 浮动垃圾（多保留一些对象） | undo log 空间占用（旧版本暂时不能清理） |

两者都是通过**记录变化**来达到逻辑快照的效果，而非物理复制数据。

## 问题41：跟CMS搭配的新生代收集器ParNew的工作流程

跟 CMS 搭配的新生代收集器是 **ParNew**（Parallel New，并行新生代收集器），是 Serial 的多线程并行版本。

### 工作流程（标记-复制算法，整个过程 STW）

```
1. STW 暂停所有应用线程
2. 标记：从 GC Roots + 卡表脏卡 → 标记 Eden + Survivor(From) 中存活对象
3. 复制：
   年龄 < MaxTenuringThreshold（最大晋升年龄阈值，默认15）→ 复制到 Survivor To，年龄+1
   年龄 ≥ 阈值 → 晋升到老年代
   Survivor To 放不下 → 直接晋升老年代
4. 清空 Eden + Survivor From
5. From 和 To 角色互换
6. 恢复应用线程
```

### 内存结构

```
新生代：Eden(80%) | Survivor From(10%) | Survivor To(10%)
比例由 -XX:SurvivorRatio（Eden与Survivor比例，默认8）控制
```

### 注意点

**① 动态年龄判定**：Survivor 中相同年龄对象总大小 > Survivor 空间 50% → 年龄 ≥ 该年龄的对象直接晋升，不一定要到 MaxTenuringThreshold。

**② 分配担保机制**：Minor GC 前检查老年代剩余空间是否够 → 不够则可能直接 Full GC → Minor GC 中晋升放不下则担保失败（Promotion Failure）→ Full GC。

**③ 线程数**：`-XX:ParallelGCThreads`（并行GC线程数），默认 = CPU 核数（≤8核时）或 3+(5×核数/8)（>8核时）。

**④ 只有 ParNew 和 Serial 能搭配 CMS**，Parallel Scavenge 不行——CMS 和 ParNew 共享卡表等内部数据结构框架。

**⑤ JDK 9+ 已废弃**，G1 成为默认收集器。

## 问题42：写屏障的实现是怎么样的，对所有对象监控不是大工程吗

写屏障**不是运行时监控**，而是**编译时插入代码**。

所有引用赋值最终是这几条字节码指令：`putfield`、`aastore`、`putstatic`。JVM 在这些指令的实现里**内嵌**了写屏障逻辑，不需要"监控"对象——所有引用修改必须通过这几条指令。

### 解释器执行时

每条 `putfield` 的解释器实现（C++ 代码）直接硬编码了写屏障：

```cpp
// 伪代码
void interpret_putfield(Object* obj, int offset, Object* new_value) {
    // Pre-Write Barrier（G1 SATB）
    Object* old_value = obj->field_at(offset);
    if (marking_active) { satb_queue->enqueue(old_value); }
    
    // 实际赋值
    obj->field_at(offset) = new_value;
    
    // Post-Write Barrier（标脏卡）
    card_table[addr_to_card(obj)] = DIRTY;
}
```

### JIT 编译后

JIT 遇到引用赋值，直接在生成的机器码中插入写屏障指令：

```asm
; Pre-Write Barrier
mov  rax, [A + field_offset]   ; 读旧值
test [marking_flag], 1          ; 并发标记是否在进行
jz   skip_satb                  ; 没有就跳过
call satb_enqueue(rax)
skip_satb:

; 实际赋值
mov  [A + field_offset], B

; Post-Write Barrier
shr  rax, 9                     ; 计算 Card 索引（地址/512）
mov  byte [card_table + rax], 0 ; 标脏卡（写1个字节）
```

### 为什么开销小

- 不是"监控所有对象"——是在赋值指令里**内嵌**几行代码
- Post-Write Barrier 每次只做 2~3 条机器指令（几纳秒）
- Pre-Write Barrier 大部分时间 marking_active=false → 一个条件判断直接跳过

### 类比

不是"派保安监控每个对象"，而是"所有引用赋值必须走赋值窗口（putfield），窗口上装了自动记录仪"。

### 性能影响

| 收集器 | 写屏障 | 吞吐量影响 |
|---|---|---|
| Parallel | 只有 Post（标脏卡） | 基准（最小） |
| CMS | 只有 Post（标脏卡） | 约 1~2% |
| G1 | Pre（SATB）+ Post（标脏卡 + RSet 维护） | 约 5~10% |

## 问题43：写屏障类似于AOP吗

对，非常像 AOP（Aspect-Oriented Programming，面向切面编程）。

| | AOP | 写屏障 |
|---|---|---|
| **切入点** | 方法匹配规则 | 所有引用赋值指令 |
| **通知** | 前置/后置增强逻辑 | Pre/Post-Write Barrier |
| **织入方式** | 编译时或动态代理 | JIT 编译时插入机器码 / 解释器硬编码 |
| **对业务的侵入** | 业务代码无感知 | Java 代码写 `A.field = B` 无感知 |

```
AOP:     @Before → 目标方法 → @After
写屏障:  Pre-Barrier → 实际赋值 → Post-Barrier
```

唯一区别：AOP 是应用层框架做的（Spring 动态代理），写屏障是 JVM 底层做的（HotSpot C++ 代码）。

**一句话：写屏障就是 JVM 层面的 AOP——对所有引用赋值操作做了无感知的前置/后置增强。**

## 问题44：CMS也是通过TAMS指针识别并发时新增对象的吗

CMS 不用 TAMS。TAMS 是 G1 特有的，因为 G1 基于 Region，每个 Region 内连续分配，才能用"水位线"区分新旧。

### CMS 为什么不能用 TAMS

CMS 的老年代用**标记-清除**算法 → 有碎片 → 用**空闲列表（Free List）**分配内存 → 新对象散布在各个空闲块中：

```
G1 Region（连续分配）：
[已用][已用][已用]│TAMS│[D][E][F]  ← 水位线以上都是新的

CMS 老年代（空闲列表分配）：
[已用][空闲][已用][新的][空闲][已用][新的][空闲]
                  ↑                  ↑
              新对象散布各处，没有统一分界线
```

### CMS 怎么处理并发标记期间新进入老年代的对象

大部分新对象分配在 Eden（CMS 不管），但有两种情况对象会进入老年代：

| 途径 | CMS 做法 |
|---|---|
| **Minor GC 晋升** | 晋升对象直接在标记位图（Mark Bitmap）中标记为存活 |
| **大对象直接分配** | 同样直接在标记位图中标记为存活 |

### 对比

| | G1 | CMS |
|---|---|---|
| **识别新对象** | TAMS 指针（水位线之上一律存活） | 逐个在标记位图中预标记 |
| **为什么不同** | Region 指针碰撞 → 有水位线 | 空闲列表分配 → 新对象分散，没有水位线 |
| **效果** | 相同——新对象一律视为存活 | 相同 |

## 问题45：CMS不是通过指针碰撞分配内存的吗

不是。**CMS 的老年代用空闲列表（Free List），不是指针碰撞（Bump Pointer）。**

指针碰撞的前提：内存规整（已用一边，空闲一边）。CMS 用标记-清除算法，不做压缩 → 碎片 → 不规整 → 不能用指针碰撞。

```
指针碰撞：[已用][已用][已用]│指针│[空闲空闲空闲]  ← 规整
CMS清除后：[存活][空闲][存活][空闲][存活][空闲]    ← 碎片
```

### 各收集器的分配方式

| 收集器/区域 | 分配方式 | 原因 |
|---|---|---|
| Serial/ParNew（新生代） | 指针碰撞 | 标记-复制 → 规整 |
| **CMS（老年代）** | **空闲列表** | **标记-清除 → 碎片** |
| Serial Old/Parallel Old | 指针碰撞 | 标记-整理 → 规整 |
| G1（每个 Region） | 指针碰撞 | Region 内标记-复制 → 规整 |

### 规律

```
标记-复制 / 标记-整理 → 规整 → 指针碰撞（快）
标记-清除            → 碎片 → 空闲列表（慢）
```

CMS 不做压缩是为了并发清除阶段不用 STW（移动对象需要暂停更新引用）。代价是碎片积累 → 找不到连续空间 → 退化为 Serial Old 做带压缩的 Full GC（单线程，STW 很长）。

## 问题46：TLAB剩余空间不够时是否浪费

### 场景

```
TLAB 100KB，已用 90KB，剩余 10KB
新对象需要 20KB → 放不下
→ 剩余 10KB 是不是浪费了？
```

### JVM 做法：refill waste 阈值决策

```
剩余空间 ≤ refill waste → 丢弃剩余，申请新 TLAB（少量浪费）
剩余空间 > refill waste → 保留 TLAB，这个大对象去 Eden 公共区域分配（CAS 竞争）
```

`refill waste = TLAB 大小 / TLABRefillWasteFraction`（TLAB重填浪费比例，默认 64）

### 被丢弃的空间

旧 TLAB "退休"（retire）→ 剩余空间被填充哑对象（dummy/filler object）→ 下次 Young GC 时随 Eden 一起回收 → 不是永久浪费。

### 实际浪费量

| 项目 | 典型值 |
|---|---|
| TLAB 大小 | 几十 KB ~ 几百 KB（动态调整） |
| 每次退休浪费 | 通常 < TLAB 的 1~2% |
| 全局浪费 | Eden 总量的 < 1% |

不到 1% 的空间浪费换来对象分配速度数倍提升（无锁 vs CAS 竞争），完全值得。
