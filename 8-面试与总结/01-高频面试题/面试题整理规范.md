# 面试题整理规范

> 本文是仓库内的面试题整理规范，不依赖外部 skill。新增、去重、改写或补充面试题时，按需阅读对应层级即可。

## 阅读方式：渐进式披露

根据当前目的选择阅读深度：

1. **只做复习**：先看高频题库中的问题、关键词和知识点链接，判断自己能否回答。
2. **需要补答案**：打开知识点文档，先看“一句话结论”和“30 秒口述版”。
3. **需要真正理解**：继续阅读知识点文档中的背景、原理、流程、边界、踩坑和追问。
4. **需要新增或维护题目**：阅读本文的“执行流程”和“题型模板”。
5. **准备提交或发布**：只看“质量检查清单”，完成必要的链接、隐私、构建和落盘校验。

## 第一层：快速规则

### 1. 题库与知识点文档分工

| 内容 | 高频面试题库 | 详细知识点文档 |
| --- | --- | --- |
| 目标 | 快速浏览、回忆和自测 | 深入理解问题为什么成立、如何实现以及边界在哪里 |
| 内容 | 问题标题、极短提示、关键词、追问方向、知识点链接 | 背景、结论、原理、流程、示例、取舍、踩坑、排查和复习清单 |
| 允许的答案长度 | 够触发记忆即可 | 按问题复杂度展开，不追求无关的百科式堆砌 |
| 链接目标 | 指向具体知识点问答或具体章节 | 作为该问题的权威解释，使用稳定的 `Qn` 标题 |
| 禁止事项 | 不复制完整原理、长流程、源码分析和排障方案 | 不把题库的简洁回答原样扩写成重复内容 |

题库回答的是“我能不能讲出来”，知识点文档回答的是“为什么、怎么实现、边界在哪里”。没有具体知识点问答时，不要为了凑链接而链接 README、目录说明或另一个题库入口；可以先补充有独立价值的知识点文档，也可以暂时不加链接。

### 2. 新增题目的最小要求

- 先搜索同义问题和已有答案，确定唯一权威归属，避免重复维护。
- 高频题库中的题目使用唯一的 `## Qn：问题` 标题，保证能够进入页面右侧大纲。
- 详细知识点文档有 `## 问题索引`，正文按 `## Q1：...`、`## Q2：...` 组织。
- 详细文档先给结论，再解释原理和流程；必要时补充边界、踩坑、追问和复习清单。
- `知识点`链接必须带锚点，并指向具体问答或具体知识章节，不指向 README 或分类入口。
- 公共文档只保留脱敏后的通用技术场景，不写个人信息、个人经历事实、组织名称、客户名称、内部数据和内部架构。

### 3. 是否值得单独成文

适合独立知识点文档的题目通常满足至少一项：

- 需要解释多个概念、组件或执行阶段，单靠几句话容易产生误解。
- 存在明确的流程、状态流转、调用链、故障排查路径或方案取舍。
- 会被多个题库、项目复盘或专题反复引用。
- 能形成有复习价值的追问链，且答案需要版本、边界或工程实践说明。

不值得单独成文的内容通常包括：

- 只需一句定义或 API 用法即可回答的低价值记忆点。
- 已有权威文档完整覆盖、仅换一种问法的问题。
- 不能形成独立结论、只属于某个大问题的零散参数或重复示例。

## 第二层：执行流程

### 1. 识别题型和整理目标

先判断输入是单题、题单、追问记录、专题文章、源码分析、故障排查还是系统设计题。明确本次是在：

- 新增题目；
- 合并同义问题；
- 从项目场景提炼通用题目；
- 将值得单独成文的问题补进知识库；
- 修复标题、目录、链接或内容质量。

不要把不同题型强行套进同一个长答案模板。

### 2. 读取结构并去重

修改前依次检查：

1. 根目录 `AGENTS.md` 和目标目录 README。
2. 目标题库中相近标题、同义问法和已有 `Qn`。
3. 知识库中是否已经有同主题的具体问答。
4. 当前目录的命名、标题层级、链接写法和 PlantUML 风格。

找到已有权威文档时，优先补充原文并增加交叉链接；只有主题边界清晰且具备独立复习价值时才新建文件。新增问题可记录元信息：

```text
技术域 / 难度 / 题型 / 版本范围 / 必答或选答 / 权威文档
```

### 3. 设计题库入口

题库中的每道题按以下最小结构组织：

```markdown
## Q1：问题

- **回忆关键词：** 关键词 1、关键词 2、关键词 3
- **回答方向：** 先讲什么，再讲什么，最后说明哪个边界
- **知识点：** [具体问答](../../目标文档.md#q1-具体问题)
```

如果题库已有较短答案，可以保留能帮助回忆的结论和关键表格，但要避免继续堆叠完整流程、源码和故障处理。问题标题必须唯一，编号连续或按当前文档既有规则维护。

### 4. 设计详细知识点文档

详细文档推荐使用以下结构：

```markdown
# 主题

## 问题索引

- Q1：问题标题
- Q2：问题标题

## Q1：问题标题

**一句话结论：** 直接回答问题本质。

**30 秒口述版：** 结论、核心机制和一个重要边界。

### 背景

为什么需要这个机制，它解决了什么问题。

### 核心原理

关键概念、数据结构、组件职责和设计原因。

### 关键流程

按输入、处理阶段、输出和失败分支解释；复杂关系再添加图示。

### 方案与取舍

实现方式、适用条件、性能和一致性边界。

### 踩坑点

常见误区、版本差异、线上风险和排查方法。

## 面试追问

- Q：高价值追问
  A：结论、理由和边界

## 复习清单

- [ ] 能用 1 分钟讲清问题背景和结论
- [ ] 能画出或描述关键流程
- [ ] 能说明方案取舍和适用边界
```

详细文档不是把题库答案换一种说法，而是沿用知识库的形式，把问题讲到读者可以理解、判断和落地的程度。简单题可以缩短结构，复杂题再增加流程图、源码链路、故障排查和版本说明。

### 5. 更新链接和导航

写入内容后同步维护：

- 高频题库中的 `知识点`链接；
- 目标技术目录的 README；
- 相关专题索引、覆盖矩阵或项目场景入口；
- 重命名、拆分或删除后的旧链接。

链接规则：

- 优先链接到具体的 `## Qn：...` 标题，必要时链接到具体知识章节。
- 不链接到 README、模块概览、分类清单、只有标题没有问答的入口或另一个高频题库文件。
- 锚点必须真实存在；不要只按原始 Markdown 标题猜测 VuePress slug，中文标点和数字标题可能影响最终 ID。
- 修改标题后重新检查构建产物中的锚点，并验证从题库点击可以定位到目标问题。

### 6. 选择图示和代码

只有图能降低理解成本时才使用：

- 简单关系优先用短文本或 ASCII 图。
- 时序、状态机、组件协作、架构拓扑、调用链和排查路径使用 PlantUML。
- 图应紧跟在它解释的知识点之后；一张图只表达一个独立关系。
- 开篇总图一般控制在 10 个关键节点以内，不把异常分支和参数细节全部塞进总图。
- 不要在文末根据全文标题和目录添加与正文脱节的总结图。

代码只保留能说明关键机制的片段，并为关键变量、关键步骤和容易误解的逻辑添加必要注释。

### 7. 落盘、验证和提交

遵循“先写文件，再回复”的顺序：

1. 将可复用内容写入对应 Markdown，而不是只停留在对话中。
2. 用搜索命中问题编号、标题和关键字，确认内容已经落盘。
3. 检查标题层级、问题索引、链接目标和 Markdown 渲染结构。
4. 公开内容执行 `npm run docs:verify`，同时检查源码和构建产物中的隐私内容。
5. 查看 `git status`、`git diff` 和 `git diff --cached`，只提交本次任务相关文件。
6. 按仓库规则创建简洁、准确的中文 Git commit。

## 第三层：题型模板

### 概念题

先给定义和本质用途，再说明关键机制、设计原因、适用条件和常见误区。不要只罗列名词。

```markdown
## Q1：问题

**一句话结论：** 定义 + 本质用途。

### 核心原理
- 关键机制
- 为什么这样设计

### 边界与误区
- 适用条件
- 常见错误或版本差异

### 高频追问
- Q：为什么不能直接用另一种方案？
  A：给出取舍和边界。
```

### 对比题

先给选择结论，再用表格比较实现、性能、一致性、复杂度和适用场景，最后给选择规则及反例。不能只堆特性而不说明如何决策。

### 原理或源码题

按“入口 → 关键组件或数据结构 → 执行链路 → 设计原因 → 异常分支 → 版本差异”组织。只引用能够确认的类、方法和调用关系，不把猜测写成源码事实。

### 流程或链路题

按“输入 → 关键阶段 → 输出”描述，先讲主流程，再补失败分支、状态变化和性能边界。流程图紧跟对应阶段，不重复解释图中已经清楚的内容。

### 故障排查题

```text
现象 → 影响范围 → 可观测证据 → 假设排序 → 定位命令或指标 → 根因 → 修复 → 验证 → 回滚与预防
```

每一步都说明“看到什么证据才进入下一步”，避免只给命令清单。

### 系统设计题

按“目标与边界 → 规模估算 → API 和数据模型 → 核心链路 → 一致性与幂等 → 容灾降级 → 监控告警 → 方案取舍”回答。先解决主链路，再补高并发、故障和扩展问题。

### 追问记录

保留问题来源和疑惑点，但开头先补一行结论，并链接回对应专题的权威问题。追问记录用于深化理解，不重新复制整篇基础答案。

## 第四层：质量检查清单

### 内容和结构

- [ ] 是否先检查 `AGENTS.md`、目标目录 README、已有文档和同义问题？
- [ ] 是否确定了唯一权威归属，避免重复维护？
- [ ] 题库是否保持快速复习定位，详细解释是否沉淀在知识点文档？
- [ ] 详细文档是否有明确问题边界、问题索引和 `Qn` 编号？
- [ ] 是否先给结论，再解释原理、流程、取舍、边界和至少一个常见坑？
- [ ] 是否只保留与回答、判断和排查直接相关的内容？
- [ ] 对比题是否先给选择结论，而不是只堆表格？
- [ ] 源码题是否区分已确认事实、版本范围和推断？
- [ ] 排查题是否包含证据、验证和回滚，而不是只有命令？
- [ ] 系统设计题是否覆盖一致性、幂等、容灾和可观测性？

### 链接和发布

- [ ] 每道题的 `Qn` 标题是否唯一，并能进入页面右侧大纲？
- [ ] 每个知识点链接是否指向具体问答或具体知识章节，而不是 README 或模块概览？
- [ ] 链接目标文件和锚点是否真实存在，标题修改后是否重新验证？
- [ ] 目录 README、专题索引和覆盖矩阵是否同步？
- [ ] 是否检查个人信息、个人经历事实、真实项目、组织名称、内部数据和内部架构？
- [ ] PlantUML 是否确实降低理解成本，并放在对应知识点附近？
- [ ] 代码是否有必要注释，是否避免大段无关实现？
- [ ] 是否搜索验证关键字并执行仓库要求的构建、公开内容校验和 Git 检查？
