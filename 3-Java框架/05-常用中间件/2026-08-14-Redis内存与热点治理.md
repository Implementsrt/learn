# Redis 内存与热点治理

## 问题索引

- Q1：Redis 内存淘汰、过期删除和内存碎片如何治理？
- Q2：Hot Key、Big Key 如何发现和处理？

## Q1：Redis 内存淘汰、过期删除和内存碎片如何治理？

**一句话结论：** 先区分“Key 到期未删除”“达到 maxmemory 被淘汰”和“分配器产生碎片”，再分别用过期策略、淘汰策略、数据拆分和实例治理解决。

### 三类问题

| 问题 | 触发条件 | 处理重点 |
| --- | --- | --- |
| 过期删除 | TTL 到期 | 惰性删除 + 定期抽样，访问时可能触发删除 |
| 内存淘汰 | 使用量达到 `maxmemory` | 选择 `noeviction`、LRU、LFU 或 TTL 相关策略 |
| 内存碎片 | 分配与释放造成空洞 | 观察 `mem_fragmentation_ratio`，必要时迁移或重建实例 |

### 处理顺序

1. 先确认业务是否允许淘汰，关键数据不要与可淘汰缓存混在同一实例。
2. 通过 `INFO memory`、慢日志、命令统计和采样定位增长来源。
3. 对大 Hash、List、Set 等拆分，控制单 Key 大小和访问复杂度。
4. 设置合理 TTL、淘汰策略和容量水位告警。
5. 碎片持续升高且无法通过主动整理缓解时，采用从库重建、分片迁移或实例替换。

## Q2：Hot Key、Big Key 如何发现和处理？

**一句话结论：** Hot Key 主要是访问集中造成单点吞吐或网络压力，Big Key 主要是单 Key 数据量或操作复杂度过大；先观测确认，再分别做副本扩散、分片拆分和异步化。

### 诊断证据

- `redis-cli --hotkeys` 或采样统计：识别访问频率异常的 Key。
- `MEMORY USAGE`、采样扫描：识别内存占用异常的 Key。
- 慢日志、命令耗时和网络流量：确认是否由单次大对象读写导致延迟。
- 业务指标：命中率、QPS、单 Key 访问分布和热点持续时间。

### 治理方案

- Hot Key：本地缓存、多副本读、Key 分片、请求合并和热点预热。
- Big Key：拆分 Hash/List、分页读取、异步删除、分批迁移，避免一次 `DEL` 阻塞主线程。
- 读写混合场景：拆分读模型和写模型，避免所有请求争抢同一 Key。
- 任何拆分都要保留版本号、过期策略和重建方案，避免只解决峰值而失去一致性。
