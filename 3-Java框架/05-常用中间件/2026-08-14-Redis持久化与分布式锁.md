# Redis 持久化与分布式锁

## 问题索引

- Q1：Redis 持久化为什么有 RDB 和 AOF？如何选择？
- Q2：如何用 Redis 实现一个相对可靠的分布式锁？

## Q1：Redis 持久化为什么有 RDB 和 AOF？如何选择？

**一句话结论：** RDB 保存某个时间点的快照，恢复快、文件小但可能丢失快照后的数据；AOF 记录写命令，数据丢失窗口更小但文件和重放成本更高，生产上常结合混合持久化与副本、备份共同设计。

### 两种日志的工作方式

| 方式 | 保存内容 | 优点 | 代价 |
| --- | --- | --- | --- |
| RDB | 某个时刻的数据快照 | 文件紧凑、恢复快、适合备份 | 两次快照之间的数据可能丢失 |
| AOF | 追加记录写命令 | 可按刷盘策略缩小丢失窗口 | 文件膨胀、重写和恢复需要重放 |
| 混合持久化 | AOF 重写时的快照 + 后续增量命令 | 兼顾恢复速度与数据完整性 | 配置和排障要理解两段格式 |

RDB 的核心问题是“快照时刻之后发生了什么”；AOF 的核心问题是“写命令什么时候真正落盘”。因此不能只用“RDB 性能高、AOF 更安全”概括，还要明确 `appendfsync` 和故障窗口：

- `always`：每次写都尝试同步，数据窗口小，但吞吐和延迟成本高。
- `everysec`：通常每秒刷盘，性能和安全性较均衡，但极端故障可能丢约一秒数据。
- `no`：交给操作系统决定，性能较好，但丢失窗口不可控。

### 选择持久化策略的思路

1. 先判断 Redis 中存放的是可重建缓存、会话状态，还是不可重新计算的业务数据。
2. 再定义可接受的 RPO（最多丢多少数据）和 RTO（多久恢复）。
3. 根据写入量、恢复数据量和磁盘能力选择 RDB、AOF 或混合持久化。
4. 通过主从、哨兵或 Cluster 提高服务可用性，但不要把副本当作备份；误删和错误写入也会被复制。
5. 定期验证备份能否恢复，观察 fork、AOF 重写、磁盘延迟和复制积压。

### 常见误区

- 开启 AOF 不代表“永不丢数据”，刷盘策略、操作系统、磁盘和故障类型都会影响结果。
- 主从复制不是持久化替代品，副本可能同时收到错误删除或过期操作。
- 只看文件是否存在不够，还要验证恢复后的数据版本、业务校验和启动耗时。

## Q2：如何用 Redis 实现一个相对可靠的分布式锁？

**一句话结论：** 加锁必须是带唯一令牌和过期时间的原子操作，解锁必须校验令牌后原子删除；如果任务可能超过租期，还要考虑续期、 fencing token 和故障转移下的安全边界。

### 基本流程

```text
生成唯一 token
  -> SET lock:key token NX PX lease
  -> 获取成功后执行业务
  -> 业务完成时用 Lua 校验 token 并删除
  -> 超时场景由续期机制或状态补偿兜底
```

示例：

```text
SET lock:order:123 <unique-token> NX PX 30000
```

不能先 `SETNX` 再单独 `EXPIRE`，否则客户端在两条命令之间宕机会留下永不过期的锁。释放锁也不能直接 `DEL`，否则持锁者 A 过期后，B 获得锁，A 恢复并执行 `DEL` 就会误删 B 的锁。

解锁脚本的核心语义是“比较值和删除必须在同一个原子操作中完成”：

```lua
-- 只有仍然持有当前 token 的客户端才能释放锁
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

### 锁并不等于业务安全

- **租期过短：** 业务尚未完成锁已过期，两个客户端可能同时执行。
- **续期失效：** 网络隔离或进程暂停可能使看门狗无法续租。
- **主从切换：** 写入主节点后尚未复制就发生故障，切换后的节点可能没有锁状态。
- **旧持有者复活：** 仅靠互斥锁不能阻止过期客户端继续写业务数据。

对高价值写操作，可以让锁服务发放单调递增的 fencing token，下游资源只接受不小于最近 token 的请求；同时在数据库用状态条件、版本号或唯一约束做第二道保护。锁适合缩小并发范围，不应替代幂等、状态机和最终一致性设计。

### 面试追问

- Q：为什么锁 value 必须是随机唯一值？
  A：用于确认释放者仍是当前持有者，避免旧客户端删除新客户端的锁。
- Q：Redisson 的看门狗解决了什么问题？
  A：在客户端仍存活且能续租时延长租期，降低业务执行时间超过固定 TTL 的风险，但不能消除进程暂停、网络隔离和主从切换问题。
