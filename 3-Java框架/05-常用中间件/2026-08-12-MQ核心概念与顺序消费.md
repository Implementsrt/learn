# MQ 核心概念与顺序消费

## 问题索引

- Q1：MQ 中生产者、消费者、Broker、Topic、Queue、消费者组分别是什么？
- Q2：MQ 如何保证消息顺序消费？

## Q1：MQ 中生产者、消费者、Broker、Topic、Queue、消费者组分别是什么？

### 背景

消息队列的核心价值是把生产消息和处理消息解耦：生产者只负责把事件交给 MQ，消费者异步处理；Broker 负责接收、存储、路由和投递。面试中容易把 Topic、Queue、Partition、Consumer Group 混为一谈，实际它们处在不同层次。

### 总体流程

~~~plantuml
@startuml
title MQ 核心角色与消息流转
actor "业务请求" as Biz
component "Producer\n生产者" as Producer
component "Broker\n消息服务端" as Broker
queue "Topic / Exchange\n路由入口" as Entry
queue "Queue / Partition\n消息顺序通道" as Lane
component "Consumer Group\n消费者组" as Group
component "Consumer\n消费者" as Consumer
database "业务数据库" as DB

Biz -> Producer : 发布事件
Producer -> Broker : 发送消息
Broker -> Entry : 接收并路由
Entry -> Lane : 写入队列或分区
Group -> Broker : 订阅 / 拉取
Broker -> Consumer : 推送或返回消息
Consumer -> DB : 执行业务处理
Consumer -> Broker : ACK / 提交 offset
@enduml
~~~

### 核心概念

| 概念 | 作用 | 需要记住的边界 |
| --- | --- | --- |
| Producer 生产者 | 创建消息并发送到 MQ | 负责序列化、路由键、发送确认、失败重试和业务唯一键 |
| Consumer 消费者 | 从 MQ 获取消息并执行处理逻辑 | 业务成功后才能 ACK；失败、超时或宕机可能触发重复投递 |
| Broker | MQ 服务端集群，负责接收、存储、路由、投递、确认、重试和高可用 | Broker 不理解订单、库存等业务语义，也不能替代业务幂等 |
| Message | 传输单元，包含 payload 和 headers/properties | 建议携带 eventId、bizKey、version、发生时间和 schemaVersion |
| Topic | 消息的逻辑分类或发布入口 | 一个 Topic 通常可以拆成多个 Queue/Partition 来扩容 |
| Queue / Partition | 实际承载消息的逻辑顺序通道 | 顺序通常只在单个 Queue/Partition 内成立，不代表 Topic 全局有序 |
| Consumer Group / Subscription | 一组消费者的协作关系和消费进度 | 同组通常分摊消息；不同组或不同订阅通常各自消费一份 |
| ACK / offset | 消费者对处理结果的确认或消费位点提交 | 业务提交成功后再确认，否则可能出现消息丢失 |
| Routing Key / Message Key | 决定消息进入哪个 Queue/Partition | 顺序消费时必须让同一业务键稳定路由到同一通道 |

### Producer：生产者

生产者是发布业务事件的应用或客户端。它通常要完成以下工作：

1. 组装消息体和消息属性。
2. 设置业务唯一键，例如 orderId、userId 或 eventId。
3. 根据 routing key 选择 Topic、Queue 或 Partition。
4. 调用同步、异步或单向发送 API。
5. 根据 Broker 返回的发送结果处理成功、失败和超时。
6. 对关键消息落本地消息表、Outbox 或使用事务消息，避免业务提交成功但消息没有发送。

发送超时不等于 Broker 没有收到消息。可能是 Broker 已经写入成功，但响应在网络中丢失；所以生产者重试可能产生重复消息，消费者仍然需要幂等。

### Consumer：消费者

消费者是读取消息并执行业务动作的应用。典型流程是：

1. 获取消息。
2. 解析消息并校验 schemaVersion、eventId 和业务字段。
3. 执行数据库更新、调用下游或发布后续事件。
4. 业务事务成功提交。
5. 返回 ACK、提交 offset 或返回消费成功。

如果第 3 步成功后应用在第 4 步前宕机，消息可能被重新投递。因此“顺序消费”必须和“幂等消费”一起设计，不能因为有顺序就认为不会重复。

### Broker：消息服务端

Broker 通常承担：

- 接收生产者发送的消息。
- 按 Topic、Exchange、Routing Key、Tag 或 Partition Key 路由消息。
- 把消息持久化到磁盘或复制到其他节点。
- 按队列、分区和订阅关系投递消息。
- 保存 ACK、消费位点、重试状态或订阅进度。
- 处理消费失败重投、死信、过期和堆积保护。
- 提供集群高可用、故障转移和流控。

Broker 只保证消息传输和存储层面的约束。例如它可以保证一个分区中的 offset 递增，但不知道消息 A 是否必须先于消息 B 修改订单状态；后者需要业务键、版本号和消费者处理逻辑共同保证。

### Topic、Queue、Partition 的关系

可以用以下层级理解：

~~~text
Broker Cluster
  -> Topic / Exchange：消息分类和路由入口
    -> Queue / Partition：实际存储与并行消费通道
      -> Consumer Group / Subscription：消费关系和进度
        -> Consumer Instance：具体处理消息的应用实例
~~~

不同 MQ 的术语映射不完全相同：

| MQ | 生产入口 | 顺序/并行单元 | 消费关系 |
| --- | --- | --- | --- |
| RocketMQ | Topic | MessageQueue | Consumer Group；顺序消费通常围绕同一队列或消息组 |
| RabbitMQ | Exchange | Queue | Consumer 绑定 Queue；Exchange 负责路由，不直接保存业务消费进度 |
| Kafka | Topic | Partition | Consumer Group 保存 partition offset，一个 partition 同组同一时刻通常只分配给一个消费者 |
| Pulsar | Topic | Partition；非分区 Topic 也可作为单通道 | Subscription 决定消费模式，如 Exclusive、Failover、Shared、Key_Shared |

### Queue 和 Consumer Group 不一样

Queue 是消息存储和投递的通道，Consumer Group 是多个消费者如何协作消费的关系：

- 同一个消费组内，消息通常由组内某一个消费者处理，适合水平扩展。
- 不同消费组可以分别订阅同一个 Topic，各自收到完整消息流，适合订单服务、积分服务、搜索服务分别消费。
- 同一个 Queue 增加消费者不一定提升并发；有些 MQ 会把消息分给多个消费者，但这会影响严格顺序。
- Queue 或 Partition 数量通常是并行度上限的重要约束。

### ACK、offset 与重投

ACK 或 offset 提交代表消费者告诉 Broker：“这一段消息已经处理完成，可以推进消费进度。”不同 MQ 的具体实现不同：

- RabbitMQ 更常见的是逐条或批量 ACK。
- Kafka 通过提交 partition offset 表示消费进度。
- RocketMQ、Pulsar 会根据消费结果、确认或订阅进度管理后续投递。

共同原则是：**确认动作要晚于业务成功提交**。如果先 ACK 再处理业务，应用宕机时可能造成消息丢失；如果处理成功但 ACK 丢失，则可能重复消费，所以需要幂等。

## Q2：MQ 如何保证消息顺序消费？

### 先定义“顺序”的范围

“保证消息顺序”不是一句无条件的承诺，首先要明确顺序单位：

| 顺序类型 | 典型做法 | 优缺点 |
| --- | --- | --- |
| 全局顺序 | 一个 Topic 只用一个 Queue/Partition，一个消费者串行处理 | 最容易理解，但吞吐低、单点阻塞明显 |
| 业务键顺序 | 用 orderId、userId 等 key 哈希到固定 Queue/Partition，同一 key 串行、不同 key 并行 | 生产上最常用，在顺序和吞吐之间平衡 |
| 因果顺序 | 消息携带 version/sequence，消费端检查前置版本 | 可支持更复杂的并发，但需要状态机、补偿和乱序缓存 |
| 无序并发 | 多 Queue/Partition、多消费者并行处理 | 吞吐高，但不能依赖消息到达顺序更新状态 |

最常见的目标不是“整个 Topic 全局有序”，而是“同一个订单或同一个用户的事件有序”。

### 顺序保证需要经过五个环节

#### 1. 先确定业务排序键

例如订单状态事件：

~~~text
order-created(orderId=O100, version=1)
order-paid(orderId=O100, version=2)
order-shipped(orderId=O100, version=3)
~~~

如果要求同一个订单按状态推进，就使用 orderId 作为顺序键，并让每条事件携带单调递增的 version。不要直接用机器时间戳判断先后，因为多实例时钟可能不一致，网络延迟也会改变到达顺序。

#### 2. 生产者必须串行化同一业务键的发送

同一个 key 即使最终路由到同一个 Queue/Partition，生产者也可能因为异步发送、多个线程或多个实例并发发送而产生不同的到达顺序：

- 同一生产者的异步发送回调完成顺序不等于调用顺序。
- 同一业务键由多个生产者实例发送时，Broker 只能看到网络到达顺序。
- 发送重试可能让后一条消息先写入。

严格顺序场景要采用以下一种或多种措施：

- 同一业务键在生产者侧进入串行发送队列。
- 同一业务键使用单独的发送线程或 per-key 锁。
- 消息带 sequence/version，消费者拒绝或暂存跳号消息。
- 多生产者场景增加统一序列号分配或按业务主键路由到固定生产实例。

顺序发送和顺序存储是两件事：生产者先后顺序没有建立起来，Broker 无法凭空恢复真正的业务顺序。

#### 3. 同一业务键必须稳定路由到同一通道

通常使用：

~~~text
queueIndex = hash(orderId) % queueCount
partition = hash(orderId) % partitionCount
~~~

相同 orderId 进入同一个 Queue/Partition，不同 orderId 可以进入不同通道并行处理。

要注意：

- 不能一部分消息带 key，另一部分不带 key。
- 不能让同一 key 在多个 Topic、Queue 或 Partition 之间随机分布。
- 扩容或改变分区数量可能改变哈希结果，导致同一 key 前后落到不同通道；严格顺序场景要设计稳定分片、迁移窗口或排空旧通道。
- RocketMQ 的顺序消息需要使用消息组/业务键；Kafka 需要稳定 partition key；Pulsar 可使用 message key 配合分区路由。

#### 4. 消费端同一通道内必须串行处理

Broker 只保证一定范围内的存储或投递顺序，应用如果把同一 Queue/Partition 的消息取出来后交给多个线程并行执行，业务处理顺序仍然可能反转。

推荐规则：

- 一个 Queue/Partition 同一时刻只由一个有序消费执行单元处理。
- 不同 Queue/Partition 可以由不同消费者并行。
- 如果使用 per-key 线程池，只能让不同 key 并行；同一 key 必须进入同一串行执行器。
- 批量拉取不等于批量并行处理。严格顺序场景应逐条处理，或保证批内同 key 的处理和提交顺序。
- 消费者发生 Rebalance、故障转移或分配变更时，旧消费者必须停止继续处理，避免新旧实例同时处理同一通道。

### PlantUML 示意图：按业务键保证顺序

~~~plantuml

P -> P : O100 事件按 version 1,2,3 串行发送
P -> T : 按 orderId 路由
T -> Q : 按存储顺序追加
Q -> C : 一次处理一条
C -> DB : 校验前置 version 并更新状态

C -> Q : ACK / 提交 offset
note right of C
前一条失败时，
后续同 key 消息不能越过
end note
@enduml
~~~

#### 5. 业务成功后再 ACK

顺序消费中最危险的错误是：

~~~text
收到 version=2
  -> 先 ACK
  -> 异步执行业务更新
  -> 更新失败或应用宕机
  -> version=3 继续处理
~~~

正确流程是：

~~~text
收到 version=2
  -> 校验 eventId、orderId、version
  -> 在本地事务中更新业务状态
  -> 成功提交
  -> ACK / 提交 offset
~~~

如果 version=2 失败，不能直接确认并让 version=3 继续改变状态；要么阻塞该顺序通道并重试，要么把消息放入带原始通道和 sequence 的补偿流程，修复后再继续。

### 重试、重复与乱序如何处理

#### 严格顺序：失败消息阻塞后续消息

同一 Queue/Partition 内，如果前一条消息失败，后续消息通常必须等待：

1. 暂停当前通道或保持消费位点不前进。
2. 按退避策略重试当前消息。
3. 达到上限后进入人工可处理的异常状态或死信。
4. 修复前置消息后，按原 sequence 重放后续消息。

这样可以保护顺序，但一条毒消息会阻塞同一通道的所有消息。因此严格顺序的业务键不宜过度集中到少数通道；RocketMQ 官方也建议不要让一个消息组承载过大的流量。

#### 业务键顺序：尽量只影响同一个 key

如果一个分区承载很多订单，理论上某个订单失败会阻塞整个分区。可以通过更多分区降低影响范围，但不能在不处理 offset/位点语义的情况下简单把同一分区消息交给多个线程并行。

更复杂的 per-key 并行方案要额外维护：

- 每个 key 的 expectedVersion。
- 跳号消息的暂存和超时告警。
- 乱序消息的重放或补偿。
- 不同 key 处理完成后如何安全提交消费位点。

如果业务不能承担这些复杂度，优先使用 MQ 原生顺序消费模式和单通道串行处理。

#### 重复消费不等于乱序消费

MQ 常见是至少一次投递。消费者处理成功但 ACK/offset 提交失败时，同一消息可能再次到达。建议同时使用：

- eventId 唯一键，避免同一事件重复执行。
- bizKey + version，拒绝旧版本或重复版本。
- 数据库唯一约束、状态机和乐观锁。
- 对跳号、旧版本、重复版本分别记录指标和日志。

可以把顺序校验抽象为：

~~~text
version < expected -> 重复或旧消息，幂等忽略
version = expected  -> 执行业务并推进状态
version > expected  -> 前置消息缺失，暂存、重试或告警
~~~

### 各种 MQ 的顺序边界

| MQ | 顺序保证的常见边界 | 破坏顺序的常见原因 |
| --- | --- | --- |
| RocketMQ | 同一 MessageQueue 或消息组内，生产、存储、投递和消费链路都按序配置 | 多线程并发发送、多个生产者、并发消费、重试后跳过失败消息 |
| RabbitMQ | 单 Queue、单消费者、无重排操作时通常接近 FIFO | 多消费者、requeue、优先级队列、异步业务线程、失败消息重新入队 |
| Kafka | 同一 Partition 内按 offset 有序；同一消费组一个分区同一时刻通常只归一个消费者 | 多 Partition 之间无全局序，消费端跨线程处理同一分区、retry topic 改变原分区顺序 |
| Pulsar | 按 routing key 将同 key 消息放入同一分区；Key_Shared 适合按 key 分配 | Shared 订阅不保证全局顺序，重投、批量并发和改变路由策略可能影响观察顺序 |

### 常见误区

1. 认为一个 Topic 天然全局有序。Topic 通常会拆成多个 Queue/Partition，顺序边界一般是单通道。
2. 认为同一个 key 就一定有序。生产者并发发送、路由变化和消费者并行处理仍然会破坏顺序。
3. 认为 MQ 顺序消费等于 exactly-once。顺序和重复是两个问题，仍需幂等。
4. 认为增加消费者线程可以提升顺序消费吞吐。同一通道通常只能串行，扩容应增加通道并按业务键分片。
5. 失败消息直接 ACK 后异步重试。这样后续消息可能越过失败消息，严格顺序会失效。
6. 把重试消息直接写回普通 Topic。重试队列可能改变分区、队列和到达顺序，必须保存原始通道和 sequence。
7. 只用 createTime 或机器时间判断先后。跨节点时钟偏差和网络延迟会让时间排序不可靠，应使用业务 sequence/version。
8. 扩容后继续沿用原有哈希假设。Queue/Partition 数量变化可能导致同一 key 改变路由，需要迁移和排空策略。

### 面试话术

> MQ 里 Producer 负责创建和发送消息，Consumer 负责拉取并处理，Broker 负责接收、持久化、路由、投递、确认和重试，Topic 是逻辑分类，Queue 或 Partition 是实际的存储和并行通道，Consumer Group 或 Subscription 描述一组消费者如何协作以及消费进度。顺序消费不能简单理解成整个 Topic 全局有序，生产上通常是按 orderId 或 userId 做业务键分片，让同一个 key 稳定进入同一个 Queue/Partition，再由单个有序消费单元串行处理，并且业务成功提交后才 ACK。前一条消息失败时不能让后一条越过，否则会造成状态乱序；同时还要用 eventId、业务版本号、唯一约束和状态机处理至少一次投递带来的重复。全局顺序可以用一个通道加一个串行消费者实现，但吞吐和故障隔离能力较差。

### 高频追问

- Q：为什么同一个 Topic 不能直接保证全局顺序？
  A：Topic 通常会拆成多个 Queue/Partition 以提高吞吐，不同通道之间没有统一的消费先后；要全局顺序只能收敛到一个通道和一个串行消费单元。

- Q：同一个订单路由到同一分区后，消费者可以开多个线程吗？
  A：严格顺序下不能直接并行处理同一分区。不同订单可以通过不同分区或受控的 per-key 串行执行器并行，但 offset 提交和失败重试必须仍然保持安全。

- Q：消息 1 失败，消息 2 是否必须等待？
  A：如果 1 和 2 属于同一顺序键，必须等待或进入能保持 sequence 的补偿流程；如果属于不同 key，可以并行，不应让一个订单的失败阻塞所有订单。

- Q：顺序消费如何处理重复消息？
  A：用 eventId 做幂等，用 bizKey + version 做状态推进。旧版本或重复版本忽略，跳号版本暂存或重试，不能只依赖 MQ 的 ACK。

- Q：生产者有多个实例，如何保证同一个 key 的发送顺序？
  A：让同一个 key 进入稳定的串行发送路径，或由统一序列号/业务版本控制；仅仅配置相同 routing key 不足以解决多个实例并发到达的问题。
