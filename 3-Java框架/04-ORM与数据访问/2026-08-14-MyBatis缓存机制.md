# MyBatis 缓存机制

## 问题索引

- Q1：MyBatis 一级缓存和二级缓存分别是什么？为什么会失效？
- Q2：MyBatis 缓存应该如何使用，哪些场景不适合开启二级缓存？

## Q1：MyBatis 一级缓存和二级缓存分别是什么？为什么会失效？

**一句话结论：** 一级缓存绑定 `SqlSession`，解决同一会话内的重复查询；二级缓存绑定 Mapper 命名空间，解决多个会话之间的部分读缓存，但它依赖提交、刷新和结果可变性，不能当作通用分布式缓存。

### 两级缓存的边界

| 缓存 | 作用域 | 默认状态 | 典型失效条件 |
| --- | --- | --- | --- |
| 一级缓存 | 当前 `SqlSession` | 默认开启 | 会话关闭、`commit`、`rollback`、`clearCache`，或执行更新导致刷新 |
| 二级缓存 | Mapper namespace | 需要配置 | 更新/提交刷新、缓存配置变化、序列化或作用域不满足 |

一级缓存的关键不是“同样的 SQL 字符串”，而是 MyBatis 生成的 `CacheKey`。通常会综合 mapped statement、分页参数、SQL、参数值和环境等信息。因此参数不同、分页不同或 SQL 经过动态拼接后结果不同，通常不会命中同一个缓存条目。

### 一级缓存为什么会失效

```text
SqlSession
  -> Executor
  -> LocalCache
  -> CacheKey
  -> 查询结果
```

同一个 `SqlSession` 中两次相同查询可能复用一级缓存；但下面的操作会改变可见性或主动清理缓存：

- 在同一会话中执行 `INSERT`、`UPDATE`、`DELETE`；
- 调用 `commit`、`rollback` 或显式 `clearCache`；
- 使用不同的 `SqlSession`；
- 参数、分页、环境或 mapped statement 不一致；
- 关闭本地缓存，或使用特殊执行器配置。

如果 Spring 每次 Mapper 调用都通过事务/会话管理器获得不同的会话，就不能把“同一个线程”误认为“同一个一级缓存作用域”。判断是否命中要看会话边界和执行配置。

## Q2：MyBatis 缓存应该如何使用，哪些场景不适合开启二级缓存？

**一句话结论：** 二级缓存只适合读多写少、数据变化边界清晰且允许短时间旧数据的查询；涉及多表更新、跨服务写入、强实时性或租户权限差异时，应优先使用明确的查询缓存或业务缓存策略。

### 二级缓存的工作方式

同一 namespace 下的查询结果可以进入共享缓存，事务提交时才适合把本地变更后的缓存状态交给共享层。不同 namespace 的更新并不知道彼此依赖，因此多表关联查询存在“一个表更新却没有刷新另一个 Mapper 缓存”的风险。

使用时需要明确：

1. 缓存 key 是否包含租户、用户权限、语言和数据范围等隔离维度。
2. 查询结果是否可序列化、是否会被调用方修改。
3. 哪些写操作会触发清理，跨 Mapper 更新是否能覆盖所有依赖。
4. 缓存容量、淘汰策略和失效后的数据库压力。
5. 多实例部署下是否需要共享缓存；二级缓存本身不等于 Redis 集群。

### 为什么复杂场景不宜直接开启

- **强一致要求：** 写入后必须立即读到新值时，缓存命中会扩大旧数据窗口。
- **多表关联：** 更新任意一张表都可能影响关联查询，namespace 刷新粒度不够。
- **权限隔离：** 如果 key 没有包含用户或租户维度，可能产生越权读取。
- **高更新数据：** 频繁清理和重建的收益很低，反而增加数据库和序列化开销。
- **跨服务写入：** 其他服务更新数据库时，MyBatis 不一定知道要清理本地缓存。

对这类场景，可以采用显式缓存层、Cache Aside、消息失效通知或直接关闭二级缓存；无论选择哪种方式，都要补充幂等、重建和故障降级策略。

### 面试追问

- Q：为什么一级缓存不会天然造成跨线程数据污染？
  A：它的作用域通常是 `SqlSession`，而 `SqlSession` 不是线程安全对象；并发场景不应共享同一个会话。
- Q：二级缓存能替代 Redis 吗？
  A：不能直接替代。二级缓存受 namespace、事务提交和应用实例边界影响，缺少通用缓存的统一过期、容量治理和跨服务一致性能力。
