# MySQL 执行计划结果详解

## 问题索引

- Q1：MySQL 执行计划每个字段分别表示什么？如何结合示例分析？
- Q2：MySQL EXPLAIN 中 partitions 表示什么？索引条件下推如何工作？

## Q1：MySQL 执行计划每个字段分别表示什么？如何结合示例分析？

### 背景

`EXPLAIN` 用来查看优化器准备采用的执行计划。它不会直接告诉我们“SQL 一定快或一定慢”，而是展示：

- 查询被拆成哪些查询块。
- 表的访问顺序。
- 每张表采用什么访问方式。
- 可能使用和实际选择的索引。
- 预计扫描多少行、过滤多少行。
- 是否需要额外排序、临时表、回表或连接缓冲。

传统表格格式通常包含 12 个字段：

~~~text
id
select_type
table
partitions
type
possible_keys
key
key_len
ref
rows
filtered
Extra
~~~

MySQL 版本、统计信息和数据分布不同，示例中的具体 `rows`、`key_len` 和优化器转换结果可能不同。分析时应关注字段语义，而不是死记某一组输出数字。

### 示例表结构

后续示例统一使用下面三张表：

~~~sql
CREATE TABLE users (
    id BIGINT NOT NULL PRIMARY KEY,
    username VARCHAR(64) NOT NULL,
    status TINYINT NOT NULL,
    UNIQUE KEY uk_username (username),
    KEY idx_status (status)
) ENGINE = InnoDB;

CREATE TABLE orders (
    id BIGINT NOT NULL PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    coupon_id BIGINT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    created_at DATETIME NOT NULL,
    KEY idx_user_id (user_id),
    KEY idx_status (status),
    KEY idx_coupon_id (coupon_id),
    KEY idx_created_at (created_at)
) ENGINE = InnoDB;

CREATE TABLE order_items (
    id BIGINT NOT NULL PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    KEY idx_order_id (order_id),
    KEY idx_product_id (product_id)
) ENGINE = InnoDB;
~~~

为了让示例更直观，假设：

- `users` 有 10 万行。
- `orders` 有 1000 万行。
- `order_items` 有 3000 万行。
- 一个用户通常有多笔订单。
- `status` 的值重复度较高。

### EXPLAIN 的几种形式

#### 传统表格格式

~~~sql
-- 查看传统的 12 列执行计划。
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

也可以写成：

~~~sql
DESCRIBE
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

在查询执行计划语境中，`DESCRIBE SELECT` 与 `EXPLAIN SELECT` 等价。

#### TREE 格式

~~~sql
-- TREE 更接近执行器的迭代器树，适合观察连接和算子层级。
EXPLAIN FORMAT = TREE
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

#### JSON 格式

~~~sql
-- JSON 会提供成本、使用到的索引列和每次扫描行数等更多属性。
EXPLAIN FORMAT = JSON
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

JSON 中常见对应关系：

| 传统字段 | JSON 属性 |
| --- | --- |
| `id` | `select_id` |
| `table` | `table_name` |
| `type` | `access_type` |
| `key_len` | `key_length` |
| `rows` | `rows_examined_per_scan` |
| `filtered` | `filtered` |
| 部分 `Extra` | `using_index`、`using_filesort`、`attached_condition` 等 |

#### EXPLAIN ANALYZE

~~~sql
-- 会真实执行 SELECT，并展示实际时间、实际行数和循环次数。
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

`EXPLAIN ANALYZE` 会真正执行 SQL。生产环境分析大查询、更新或删除语句前，必须先评估影响；它固定使用 TREE 格式，不能把它当成无副作用的普通 `EXPLAIN`。

### 应该按什么顺序阅读执行计划

~~~plantuml
@startuml
title MySQL 执行计划阅读顺序
start
:确认查询块\nid、select_type;
:确认访问顺序\ntable;
:判断访问范围\ntype;
:检查索引\npossible_keys、key、key_len、ref;
:估算数据量\nrows × filtered;
:检查附加动作\nExtra;
:使用 EXPLAIN ANALYZE\n对比估算与实际;
stop
@enduml
~~~

推荐顺序：

1. 先看 `id`、`select_type`，识别主查询、子查询、派生表和 UNION。
2. 再看同一查询块中表的出现顺序，理解驱动表和被驱动表。
3. 看 `type`，判断全表扫描、索引扫描、范围扫描还是点查。
4. 看 `possible_keys`、`key`、`key_len`、`ref`，判断索引为什么可用、实际用了多少。
5. 看 `rows × filtered / 100`，估算传递给下一步的行数。
6. 看 `Extra`，识别回表过滤、额外排序、临时表和覆盖索引。
7. 最后用 `EXPLAIN ANALYZE` 对比估算与实际，不要只凭传统 EXPLAIN 下结论。

### 一份完整输出示例

SQL：

~~~sql
EXPLAIN
SELECT u.username, o.id, o.amount
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.id = 1001
  AND o.status = 1;
~~~

可能得到以下代表性结果：

| id | select_type | table | partitions | type | possible_keys | key | key_len | ref | rows | filtered | Extra |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | ---: | ---: | --- |
| 1 | SIMPLE | u | NULL | const | PRIMARY | PRIMARY | 8 | const | 1 | 100.00 | NULL |
| 1 | SIMPLE | o | NULL | ref | idx_user_id,idx_status | idx_user_id | 8 | const | 50 | 10.00 | Using where |

可以先粗略解释为：

- `u` 通过主键常量查询，最多返回一行，因此是 `const`。
- `o` 使用 `idx_user_id` 查出该用户的订单，因此是 `ref`。
- 优化器预计读取约 50 条订单。
- `filtered=10.00` 表示预计只有约 10% 能满足 `status=1`。
- 预计传给下一步或客户端的订单约为 `50 × 10% = 5` 行。
- `Using where` 表示读取到候选记录后，还要继续判断 `status=1`。

具体 `rows` 会随统计信息变化，该输出只用于解释字段之间的关系。

### 十二个字段逐项详解

#### 1. id：查询块编号

`id` 是 SELECT 查询块的标识。它不是表的编号，也不是严格的执行步骤编号。

常见理解规则：

- 简单查询通常只有一个 `id=1`。
- 子查询、派生表、UNION 可能产生多个 id。
- 同一个 id 出现多行，通常表示这些表属于同一个查询块。
- UNION 汇总行的 id 可能是 NULL，`table` 显示为 `<union M,N>`。
- 不能只按 id 从大到小机械推断现代 MySQL 的真实运行时序，优化器可能做半连接、物化和派生表合并。

简单查询：

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE id = 100;
~~~

代表性结果：

| id | select_type | table |
| --- | --- | --- |
| 1 | SIMPLE | orders |

子查询示例：

~~~sql
EXPLAIN
SELECT *
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
    WHERE amount > 1000
);
~~~

可能看到多个查询块，也可能因为半连接或物化优化而改变显示方式。判断时要把 `id` 与 `select_type`、`table` 一起看。

#### 2. select_type：SELECT 的类型

`select_type` 描述当前查询块在整条 SQL 中扮演什么角色。

| 值 | 含义 | 示例或场景 |
| --- | --- | --- |
| `SIMPLE` | 不包含子查询和 UNION 的简单查询 | `SELECT * FROM orders` |
| `PRIMARY` | 最外层 SELECT | 外层查询包含子查询或 UNION |
| `UNION` | UNION 中第二个及后续 SELECT | `SELECT id FROM users UNION SELECT id FROM orders` |
| `DEPENDENT UNION` | UNION 分支依赖外层查询 | 相关子查询内部包含 UNION |
| `UNION RESULT` | UNION 结果汇总 | `table` 常显示 `<union1,2>` |
| `SUBQUERY` | 子查询中的第一个 SELECT | 不依赖外层行的普通子查询 |
| `DEPENDENT SUBQUERY` | 依赖外层行的相关子查询 | 子查询引用外层表字段 |
| `DERIVED` | FROM 中的派生表 | `FROM (SELECT ...) d` |
| `DEPENDENT DERIVED` | 依赖其他表的派生表 | LATERAL 派生表等场景 |
| `MATERIALIZED` | 子查询结果被物化 | IN 子查询被保存为内部临时结果 |
| `UNCACHEABLE SUBQUERY` | 结果不能缓存，需要重复评估 | 使用某些非确定性表达式或依赖外部状态 |
| `UNCACHEABLE UNION` | 不可缓存子查询中的后续 UNION 分支 | 较少见 |

##### SIMPLE 示例

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE id = 100;
~~~

`select_type=SIMPLE`。

##### PRIMARY 与 SUBQUERY 示例

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE amount > (
    SELECT AVG(amount)
    FROM orders
);
~~~

外层通常是 `PRIMARY`，内层可能是 `SUBQUERY`。优化器也可能把不相关子查询提前计算。

##### DERIVED 示例

~~~sql
EXPLAIN
SELECT d.user_id, d.total_amount
FROM (
    SELECT user_id, SUM(amount) AS total_amount
    FROM orders
    GROUP BY user_id
) AS d
WHERE d.total_amount > 10000;
~~~

派生表查询块可能显示 `DERIVED`，外层访问对象可能显示 `<derived2>`。如果优化器能够合并派生表，输出可能不同。

##### DEPENDENT SUBQUERY 示例

~~~sql
EXPLAIN
SELECT u.id
FROM users u
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.user_id = u.id
      AND o.status = u.status
);
~~~

子查询引用了外层的 `u.id` 和 `u.status`，逻辑上属于相关子查询。但 MySQL 可能将它转换为半连接，因此不保证一定显示 `DEPENDENT SUBQUERY`。

##### UNION 示例

~~~sql
EXPLAIN
SELECT id FROM users WHERE status = 1
UNION
SELECT user_id FROM orders WHERE status = 1;
~~~

可能出现 `PRIMARY`、`UNION` 和 `UNION RESULT`。如果使用 `UNION ALL`，不需要去重，计划可能更简单。

#### 3. table：当前访问对象

`table` 表示这一行执行计划正在访问的表或内部结果。

常见形式：

| 显示值 | 含义 |
| --- | --- |
| `orders` | 真实表 |
| `o` | SQL 中定义的表别名 |
| `<derived2>` | 来自 id=2 的派生表结果 |
| `<union1,2>` | id=1 和 id=2 的 UNION 结果 |
| `<subquery2>` | 被物化的子查询结果 |
| `<temporary N>` | 某些内部临时结果，具体显示与版本和格式有关 |

示例：

~~~sql
EXPLAIN
SELECT *
FROM (
    SELECT user_id, COUNT(*) AS order_count
    FROM orders
    GROUP BY user_id
) AS summary
WHERE summary.order_count > 10;
~~~

外层访问对象可能显示为 `<derived2>`，表示它不是磁盘上的真实表名，而是查询块 2 产生的结果。

对于同一个 `id` 的多表连接，传统 EXPLAIN 中表行的顺序通常反映优化器选择的访问顺序：先出现的是驱动侧，后出现的是被驱动侧。但哈希连接和 TREE 计划应结合算子树理解。

#### 4. partitions：匹配的分区

`partitions` 表示分区表经过分区裁剪后，需要访问哪些分区。非分区表通常为 NULL。

示例分区表：

~~~sql
CREATE TABLE order_archive (
    id BIGINT NOT NULL,
    created_at DATE NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    PRIMARY KEY (id, created_at)
)
PARTITION BY RANGE COLUMNS (created_at) (
    PARTITION p2025 VALUES LESS THAN ('2026-01-01'),
    PARTITION p2026 VALUES LESS THAN ('2027-01-01'),
    PARTITION pmax VALUES LESS THAN (MAXVALUE)
);
~~~

查询：

~~~sql
EXPLAIN
SELECT *
FROM order_archive
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01';
~~~

理想情况下 `partitions=p2026`，说明发生分区裁剪。如果显示多个不相关分区，需要检查：

- 查询条件是否包含分区键。
- 分区键上是否发生函数计算或隐式转换。
- 条件能否在优化阶段确定。
- 分区设计是否与访问模式一致。

分区裁剪减少的是需要访问的分区，不代表分区内部一定使用索引。

#### 5. type：访问类型

`type` 在 JSON 中对应 `access_type`。它描述 MySQL 如何从当前表中找到候选行，是判断扫描范围的核心字段。

官方文档通常按从更精确到更宽泛的顺序列出：

~~~text
system
const
eq_ref
ref
fulltext
ref_or_null
index_merge
unique_subquery
index_subquery
range
index
ALL
~~~

这不是可以脱离数据量和总成本使用的绝对性能排行榜。例如：

- 小表的 `ALL` 可能比走索引回表更快。
- `range` 扫描 500 万行可能比 `ref` 扫描 5 行慢很多。
- `index` 虽然扫描的是索引，但仍可能扫描完整棵索引。
- 最终必须结合 `rows`、`filtered`、回表、排序和实际耗时判断。

##### system

表只有一行，是 `const` 的特殊情况。实际业务 InnoDB 表中较少见，不能为了追求 `system` 做优化。

##### const

通过主键或 UNIQUE NOT NULL 索引的完整等值条件，最多匹配一行，查询开始时读取一次。

~~~sql
EXPLAIN
SELECT *
FROM users
WHERE id = 1001;
~~~

典型结果：

~~~text
type=const
key=PRIMARY
ref=const
rows=1
~~~

##### eq_ref

对前面表的每一行，当前表通过主键或唯一非空索引最多匹配一行，常见于唯一键连接。

~~~sql
EXPLAIN
SELECT oi.id, o.amount
FROM order_items oi
JOIN orders o ON o.id = oi.order_id
WHERE oi.id BETWEEN 100 AND 200;
~~~

如果先范围读取 `oi`，再通过 `o.id` 查询订单，`o` 可能是：

~~~text
type=eq_ref
key=PRIMARY
ref=demo.oi.order_id
rows=1
~~~

##### ref

使用普通非唯一索引或唯一索引的部分前缀进行等值查找，可能返回多行。

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

典型结果：

~~~text
type=ref
key=idx_user_id
ref=const
~~~

##### fulltext

使用 FULLTEXT 全文索引。

~~~sql
CREATE FULLTEXT INDEX ft_username ON users (username);

EXPLAIN
SELECT *
FROM users
WHERE MATCH(username) AGAINST('alice' IN NATURAL LANGUAGE MODE);
~~~

可能显示 `type=fulltext`。真实项目更常对文章标题、正文等文本列建立全文索引。

##### ref_or_null

先按索引值查找，再额外查找 NULL。

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE coupon_id = 200
   OR coupon_id IS NULL;
~~~

`idx_coupon_id` 可用时可能显示 `type=ref_or_null`。

##### index_merge

同时使用多个索引，再对结果求交集、并集或排序并集。

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001
   OR status = 9;
~~~

可能显示：

~~~text
type=index_merge
key=idx_user_id,idx_status
Extra=Using union(idx_user_id,idx_status)
~~~

`index_merge` 不一定比一个合适的联合索引更好。大量结果集合并、去重和回表仍可能很贵。

##### unique_subquery

某些 `IN (SELECT 主键或唯一键 ...)` 子查询可以转化为唯一索引查找。

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id IN (
    SELECT id
    FROM users
    WHERE status = 1
);
~~~

优化器可能显示 `unique_subquery`，也可能使用物化或半连接，取决于版本、统计信息和改写结果。

##### index_subquery

与 `unique_subquery` 类似，但子查询使用非唯一索引，可能返回多个匹配值。

~~~sql
EXPLAIN
SELECT *
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
    WHERE status = 1
);
~~~

现代 MySQL 常将此类查询改写为半连接或物化，因此示例不保证固定出现该访问类型。

##### range

使用索引读取一个或多个范围。

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE created_at >= '2026-07-01'
  AND created_at < '2026-08-01';
~~~

典型结果：

~~~text
type=range
key=idx_created_at
ref=NULL
~~~

`BETWEEN`、`>`、`>=`、`<`、`<=`、`IN`、可利用前缀的 `LIKE 'abc%'` 等都可能产生 `range`。

##### index

扫描完整索引，而不是按明确范围定位。它通常比 `ALL` 少读取一些数据，尤其是覆盖索引更窄时，但本质仍可能是全索引扫描。

~~~sql
EXPLAIN
SELECT created_at
FROM orders
ORDER BY created_at;
~~~

如果直接扫描 `idx_created_at`，可能显示：

~~~text
type=index
key=idx_created_at
Extra=Using index
~~~

这里 `Using index` 表示覆盖索引，不代表只读取少量行。

##### ALL

全表扫描。

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE amount = 99.99;
~~~

`amount` 没有索引时通常显示：

~~~text
type=ALL
key=NULL
Extra=Using where
~~~

对千万级表需要重点关注，但小表、低选择性查询或需要读取大部分数据时，全表扫描可能是合理计划。

#### 6. possible_keys：理论候选索引

`possible_keys` 表示根据 WHERE、JOIN 等条件，优化器认为可能用于查找当前表记录的索引。

示例：

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001
  AND status = 1;
~~~

可能显示：

~~~text
possible_keys=idx_user_id,idx_status
key=idx_user_id
~~~

含义是：

- 两个索引在语法和条件上都有使用可能。
- 优化器最终认为 `idx_user_id` 成本更低。
- `possible_keys` 不是“应该使用的索引列表”。
- 列表中有索引，不代表使用它一定更快。

`possible_keys=NULL` 表示没有找到适合定位记录的索引。但 `key` 偶尔仍可能出现一个覆盖索引，因为优化器可能选择扫描更窄的索引来替代全表扫描。

#### 7. key：实际选择的索引

`key` 表示优化器实际选择的索引。

可能情况：

| key | 含义 |
| --- | --- |
| `PRIMARY` | 使用主键 |
| `uk_username` | 使用唯一索引 |
| `idx_user_id` | 使用普通二级索引 |
| 多个索引名 | `index_merge` 使用多个索引 |
| NULL | 没有使用索引访问路径 |

示例：

~~~sql
EXPLAIN
SELECT *
FROM users
WHERE username = 'alice';
~~~

可能显示：

~~~text
possible_keys=uk_username
key=uk_username
type=const
~~~

注意：

- `key=NULL` 不一定表示 SQL 必须优化，小表全扫可能合理。
- `key` 有值也不代表高效，索引可能扫描大量记录。
- `FORCE INDEX` 只能改变候选决策，不能修复错误的数据模型和返回量。
- 应结合 `type`、`rows`、`filtered`、`Extra` 和实际耗时分析。

#### 8. key_len：实际使用的索引键最大字节长度

`key_len` 表示优化器在当前访问路径中使用的索引键长度。它是最大可能长度，不是磁盘上本次实际读取的字节数。

它主要用于：

- 判断联合索引使用到了哪些前缀列。
- 判断字符串索引前缀使用长度。
- 观察可空列、字符集和变长字段对索引长度的影响。

常见粗略计算：

| 类型 | 常见键长度 |
| --- | ---: |
| `TINYINT NOT NULL` | 1 字节 |
| `INT NOT NULL` | 4 字节 |
| `BIGINT NOT NULL` | 8 字节 |
| `DATE NOT NULL` | 3 字节 |
| `DATETIME NOT NULL` | 5 字节 |
| 可为 NULL | 通常额外增加 NULL 标记字节 |
| `VARCHAR(N)` | 字符最大字节数，加变长长度字节，nullable 时再考虑 NULL 标记 |

实际长度还受 MySQL 版本、字符集、排序规则、前缀索引和内部编码影响，不应只靠背公式。

创建联合索引：

~~~sql
ALTER TABLE orders
ADD INDEX idx_tenant_status_created (
    tenant_id,
    status,
    created_at
);
~~~

查询一：

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE tenant_id = 10;
~~~

`key_len` 可能只对应 `tenant_id` 的 8 字节。

查询二：

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE tenant_id = 10
  AND status = 1;
~~~

`key_len` 可能对应 `tenant_id + status`，约 9 字节。

查询三：

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE tenant_id = 10
  AND status = 1
  AND created_at >= '2026-07-01';
~~~

`key_len` 可能进一步包含 `created_at`。但范围条件之后的列通常不能继续用于缩小索引扫描边界，是否出现在 `key_len` 中要结合具体计划判断。

对于 `index_merge`，`key_len` 可能显示多个索引各自使用的最长键长度。

#### 9. ref：索引与什么值比较

`ref` 表示查找索引时，索引列与哪个常量、列或表达式比较。

常见值：

| ref | 含义 |
| --- | --- |
| `const` | 与常量比较 |
| `库名.表名.列名` | 与前面表的某列比较 |
| `func` | 与函数或表达式结果比较 |
| NULL | 当前访问方式不需要等值引用，例如 range、index、ALL |

常量查询：

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

可能显示：

~~~text
key=idx_user_id
ref=const
~~~

连接查询：

~~~sql
EXPLAIN
SELECT u.id, o.id
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.status = 1;
~~~

`o` 可能显示：

~~~text
key=idx_user_id
ref=demo.u.id
~~~

表示对每个先读取到的用户，用 `u.id` 查询订单索引。

#### 10. rows：预计检查的行数

`rows` 是优化器估计当前表每次扫描需要检查的行数，不是最终返回行数，也不是精确值。

示例：

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE status = 1;
~~~

如果显示：

~~~text
rows=5000000
filtered=100.00
~~~

表示优化器预计通过当前访问方式检查约 500 万行。它并不表示客户端一定收到 500 万行，后续还有连接、过滤、聚合和 LIMIT。

InnoDB 的 `rows` 来自采样统计信息和成本估算，可能因为以下原因失真：

- 统计信息过期。
- 默认采样页数不足。
- 数据严重倾斜。
- 多列相关性无法准确表达。
- 直方图缺失。
- 查询参数恰好是热点值或冷门值。

`EXPLAIN ANALYZE` 中 estimated rows 与 actual rows 差距很大时，应优先处理统计信息、直方图、索引和数据分布问题。

#### 11. filtered：存储引擎返回后预计保留比例

`filtered` 表示当前表读取到的候选行中，预计有多少百分比能通过表级条件并传递给下一步。

估算传递行数：

~~~text
预计输出行数
≈ rows × filtered / 100
~~~

示例：

~~~text
rows=100000
filtered=5.00
~~~

表示预计检查 10 万行，其中约 5% 通过条件，约 5000 行进入下一步。

查询：

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001
  AND status = 1;
~~~

如果使用 `idx_user_id`：

~~~text
rows=50
filtered=10.00
Extra=Using where
~~~

说明索引先找到该用户约 50 笔订单，再由 `status=1` 过滤到约 5 行。

多表连接中，前面表的 `rows × filtered` 误差会被后续循环放大，因此需要优先关注驱动表输出量和连接层级的估算误差。

#### 12. Extra：额外执行信息

`Extra` 是最容易被误读的字段。它描述无法完全由其他列表达的附加动作，例如覆盖索引、条件下推、额外排序、临时表和连接算法。

##### 常见 Extra 值

| Extra | 具体含义 | 常见关注点 |
| --- | --- | --- |
| `Using where` | 读取候选行后继续应用 WHERE 条件 | 很常见，不等于一定慢 |
| `Using index` | 覆盖索引，所需列都能从索引获得 | 减少回表，但仍可能扫描很多索引项 |
| `Using index condition` | 使用索引条件下推 ICP，先在索引层过滤再决定是否回表 | 能减少回表，不等于覆盖索引 |
| `Using filesort` | 不能直接按目标顺序从索引得到结果，需要额外排序 | filesort 不一定写磁盘，但大结果排序需关注 |
| `Using temporary` | 需要内部临时表保存中间结果 | 常见于 GROUP BY、DISTINCT、复杂排序 |
| `Using join buffer (...)` | 使用连接缓冲、BKA 或 hash join | 常提示被连接列无合适索引或优化器选择哈希连接 |
| `Using index for group-by` | 利用索引高效完成 GROUP BY 或 DISTINCT | 通常是较好的分组访问方式 |
| `Using MRR` | 使用 Multi-Range Read，先整理主键再批量回表 | 减少随机 IO |
| `Using union(...)` | Index Merge 对多个索引结果取并集 | 检查是否应设计联合索引 |
| `Using intersect(...)` | Index Merge 对多个索引结果取交集 | 多索引合并未必优于联合索引 |
| `Backward index scan` | 反向扫描降序索引 | 常和 `Using index` 一起出现 |
| `Select tables optimized away` | 聚合可直接通过索引或元数据完成 | 例如某些 MIN/MAX 查询 |
| `Impossible WHERE` | 优化阶段判断 WHERE 永远不成立 | 不访问或极少访问表 |
| `No matching row in const table` | const 表没有匹配记录 | 后续查询可能直接结束 |
| `Not exists` | 可利用反连接语义，找到匹配后停止 | 常见于 LEFT JOIN ... IS NULL |
| `Range checked for each record` | 没有固定理想索引，对前表每行重新判断范围索引 | 通常需要重点优化 |
| `FirstMatch(...)` | 半连接 FirstMatch 策略 | 找到首个匹配后跳过后续重复匹配 |
| `LooseScan(...)` | 半连接或分组的 LooseScan 策略 | 利用索引跳过重复值 |
| `Materialize` | 物化子查询或派生结果 | 关注物化数据量与是否重复使用 |

##### Using where

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001
  AND status = 1;
~~~

只使用 `idx_user_id` 时，`status=1` 需要额外判断，通常显示 `Using where`。

不要把 `Using where` 当成错误。几乎所有带过滤条件的 SQL 都可能出现它，关键是过滤发生前读取了多少行。

##### Using index

~~~sql
EXPLAIN
SELECT user_id
FROM orders
WHERE user_id = 1001;
~~~

`idx_user_id` 同时包含查询条件和返回列，可能显示 `Using index`，表示不需要回表读取完整订单行。

注意：

~~~text
type=index + Extra=Using index
~~~

仍可能是完整覆盖索引扫描；覆盖索引减少单行成本，但不自动减少扫描行数。

##### Using index condition

~~~sql
ALTER TABLE orders
ADD INDEX idx_user_amount (user_id, amount);

EXPLAIN
SELECT *
FROM orders
WHERE user_id > 1000
  AND amount > 500;
~~~

如果 `user_id` 形成范围，`amount` 不能继续完整缩小索引边界，但可以在二级索引记录上先判断，可能显示 `Using index condition`。只有通过条件的记录才回表。

区别：

| Extra | 是否回表 |
| --- | --- |
| `Using index` | 通常不回表，属于覆盖索引 |
| `Using index condition` | 仍可能回表，但先通过 ICP 减少回表次数 |

##### Using filesort

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE status = 1
ORDER BY amount DESC;
~~~

如果没有能同时支持过滤和排序的索引，通常显示 `Using filesort`。

filesort 是 MySQL 的额外排序算法名称，不表示一定使用磁盘文件。结果较小时可以在内存排序，超过内存或数据量较大时可能使用临时文件。

##### Using temporary

~~~sql
EXPLAIN
SELECT status, COUNT(*)
FROM orders
GROUP BY status
ORDER BY COUNT(*) DESC;
~~~

分组字段与排序表达式不同，可能需要内部临时表，并出现 `Using temporary; Using filesort`。

优化时要结合数据量考虑：

- 是否有匹配 GROUP BY 的索引。
- 是否可以减少参与聚合的数据。
- 是否需要预聚合或汇总表。
- 临时表是否可能落盘。

##### Using join buffer

~~~sql
EXPLAIN
SELECT *
FROM orders o
JOIN order_items oi ON oi.product_id = o.tenant_id;
~~~

即使两列业务语义可能不合理，这个示例用于说明：连接条件缺少合适索引时，可能看到 `Using join buffer (hash join)` 等信息。

MySQL 8.x 可以对无索引等值连接使用哈希连接。出现 join buffer 不应只理解为“必然使用 Nested Loop”，要结合 TREE 格式查看实际算子。

#### select_type、type 和 Extra 不要混淆

| 字段 | 回答的问题 |
| --- | --- |
| `select_type` | 这是主查询、子查询、派生表还是 UNION？ |
| `type` | 当前表如何寻找候选行？ |
| `Extra` | 寻找候选行之外还做了哪些操作？ |

例如：

~~~text
select_type=SIMPLE
type=range
Extra=Using index condition; Using where
~~~

表示：

- 这是简单查询。
- 通过索引范围找到候选记录。
- 在索引层做部分条件下推。
- 仍有剩余 WHERE 条件需要判断。

### EXPLAIN ANALYZE 结果详解

#### 代表性输出

~~~sql
EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

可能输出：

~~~text
-> Index lookup on orders using idx_user_id (user_id=1001)
   (cost=5.20 rows=50)
   (actual time=0.080..0.210 rows=42 loops=1)
~~~

字段解释：

| 内容 | 含义 |
| --- | --- |
| `cost=5.20` | 优化器估算成本单位，不直接等于毫秒 |
| `rows=50` | 优化器预计每次循环返回 50 行 |
| `actual time=0.080..0.210` | 平均每次循环首行时间到完成时间，单位毫秒 |
| `actual rows=42` | 平均每次循环实际返回 42 行 |
| `loops=1` | 当前迭代器执行一次 |

当 `loops>1` 时，`actual time` 和 `rows` 通常是每次循环的平均值。粗略总处理量可以理解为：

~~~text
actual rows × loops
~~~

但父子迭代器耗时包含关系复杂，不能把树中所有节点耗时简单相加。

#### 多表连接中的 loops

~~~sql
EXPLAIN ANALYZE
SELECT u.id, o.id
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.status = 1;
~~~

代表性片段：

~~~text
-> Nested loop inner join
   -> Index lookup on users using idx_status (status=1)
      (actual rows=1000 loops=1)
   -> Index lookup on orders using idx_user_id (user_id=users.id)
      (actual rows=20 loops=1000)
~~~

含义：

- 先读取约 1000 个用户。
- 对每个用户执行一次订单索引查询。
- 订单节点执行约 1000 次。
- 订单平均每次返回 20 行。
- 订单层总输出量约为 `20 × 1000 = 2 万行`。

因此分析连接计划时，`loops` 往往比单看每次 `rows` 更重要。

#### 如何判断估算失真

重点计算：

~~~text
估算偏差倍数
≈ actual rows / estimated rows
~~~

例如：

~~~text
estimated rows=10
actual rows=100000
~~~

说明基数估算相差约一万倍。常见原因：

- 统计信息过期。
- 数据严重倾斜。
- 直方图缺失。
- 多列相关性被低估。
- 联合索引前缀统计无法表达真实条件组合。

纠正顺序：

1. 执行 `ANALYZE TABLE`。
2. 检查 `mysql.innodb_table_stats` 和 `mysql.innodb_index_stats`。
3. 对倾斜列创建直方图。
4. 调整采样页数。
5. 建立能表达多列关系的联合索引。
6. 最后才考虑 Hint 或 `FORCE INDEX`。

### 典型执行计划示例

#### 示例一：主键点查

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE id = 10001;
~~~

预期重点：

~~~text
type=const
key=PRIMARY
key_len=8
ref=const
rows=1
~~~

结论：主键完整等值查询，通常是很稳定的访问方式。

#### 示例二：普通二级索引等值查询

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001;
~~~

预期重点：

~~~text
type=ref
key=idx_user_id
rows=该用户的预计订单数
~~~

如果返回所有列，需要根据二级索引中的主键回表。

#### 示例三：范围查询

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE created_at >= '2026-07-01'
  AND created_at < '2026-08-01';
~~~

预期重点：

~~~text
type=range
key=idx_created_at
ref=NULL
~~~

如果时间范围覆盖大部分表，优化器也可能放弃索引改用 `ALL`。

#### 示例四：全表扫描

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE amount = 99.99;
~~~

预期重点：

~~~text
type=ALL
key=NULL
Extra=Using where
~~~

是否添加 `amount` 索引，要结合查询频率、选择性、更新成本和返回行数判断。

#### 示例五：覆盖索引

~~~sql
EXPLAIN
SELECT user_id
FROM orders
WHERE user_id = 1001;
~~~

预期重点：

~~~text
type=ref
key=idx_user_id
Extra=Using index
~~~

说明查询列全部在二级索引中，不需要回表。

#### 示例六：额外排序

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE status = 1
ORDER BY created_at DESC
LIMIT 20;
~~~

现有单列索引下可能出现：

~~~text
key=idx_status
Extra=Using where; Using filesort
~~~

添加联合索引：

~~~sql
-- 等值过滤列在前，排序列在后，尝试同时支持过滤和排序。
ALTER TABLE orders
ADD INDEX idx_status_created (status, created_at DESC);
~~~

重新执行 EXPLAIN，理想情况下可以按索引顺序读取，`Using filesort` 消失。但如果 `status=1` 覆盖绝大多数行，仍需验证实际扫描量。

#### 示例七：联合索引与 key_len

索引：

~~~sql
ALTER TABLE orders
ADD INDEX idx_tenant_status_created (
    tenant_id,
    status,
    created_at
);
~~~

查询：

~~~sql
EXPLAIN
SELECT id, created_at
FROM orders
WHERE tenant_id = 10
  AND status = 1
ORDER BY created_at DESC
LIMIT 20;
~~~

重点检查：

- `key=idx_tenant_status_created`。
- `key_len` 是否包含 `tenant_id + status`。
- `type` 是否为 `ref` 或合理的范围访问。
- `Extra` 是否仍有 `Using filesort`。
- 是否为覆盖索引。
- `rows` 是否符合该租户、状态的数据量。

#### 示例八：驱动表与 eq_ref

~~~sql
EXPLAIN
SELECT oi.id, o.id, o.amount
FROM order_items oi
JOIN orders o ON o.id = oi.order_id
WHERE oi.product_id = 9001;
~~~

理想结构：

~~~text
oi: type=ref,    key=idx_product_id
o : type=eq_ref, key=PRIMARY, ref=oi.order_id, rows=1
~~~

先通过产品索引找到订单项，再对每条订单项通过订单主键查询唯一订单。

#### 示例九：索引合并

~~~sql
EXPLAIN
SELECT *
FROM orders
WHERE user_id = 1001
   OR status = 9;
~~~

可能出现：

~~~text
type=index_merge
key=idx_user_id,idx_status
Extra=Using union(idx_user_id,idx_status)
~~~

如果这是高频核心 SQL，应评估：

- 是否可以拆成 `UNION ALL` 后分别利用索引。
- 是否存在重复行，是否需要去重。
- 两个条件各自返回多少数据。
- 业务上是否能够改写查询入口。

#### 示例十：临时表与排序

~~~sql
EXPLAIN
SELECT user_id, COUNT(*) AS order_count
FROM orders
WHERE created_at >= '2026-01-01'
GROUP BY user_id
ORDER BY order_count DESC
LIMIT 100;
~~~

可能出现：

~~~text
Using where; Using temporary; Using filesort
~~~

这不代表一定有简单索引可以消除全部操作。聚合后按计算结果排序，本身就可能需要临时结果和额外排序。应考虑缩小数据范围、离线汇总或预聚合表。

### 一个完整优化案例

#### 原 SQL

~~~sql
EXPLAIN ANALYZE
SELECT id, amount, created_at
FROM orders
WHERE tenant_id = 10
  AND status = 1
  AND created_at >= '2026-07-01'
ORDER BY created_at DESC
LIMIT 20;
~~~

现有索引只有 `idx_status` 和 `idx_created_at` 时，优化器可能：

- 使用 `idx_status` 后扫描大量状态相同的订单。
- 使用 `idx_created_at` 后逐条判断租户和状态。
- 产生大量回表和 `Using where`。
- 为最终顺序执行 `Using filesort`，具体取决于选中的路径。

#### 建立联合索引

~~~sql
-- tenant_id、status 为等值条件，created_at 同时用于范围与排序。
ALTER TABLE orders
ADD INDEX idx_tenant_status_created (
    tenant_id,
    status,
    created_at DESC
);
~~~

优化后期望：

~~~text
key=idx_tenant_status_created
type=range 或 ref
key_len 覆盖 tenant_id、status，并可能使用 created_at 范围
rows 明显下降
Using filesort 消失或排序成本明显下降
~~~

由于 SELECT 的 `amount` 不在索引中，仍可能回表。是否把 `amount` 加入覆盖索引，需要权衡：

- 查询频率。
- 回表次数。
- 索引大小。
- 写入放大。
- Buffer Pool 占用。
- 金额列是否经常更新。

#### 验证优化结果

不要只看 `key` 是否变了，应比较：

~~~text
estimated rows
actual rows
loops
actual time
rows examined
是否回表
是否 filesort
执行多组热门值与冷门值后的稳定性
~~~

优化器可能因为数据分布变化重新选择计划，所以要对不同租户、状态和时间范围进行回归。

### 常见误区

1. 认为 `type` 只要不是 ALL，SQL 就一定快。
2. 认为 `key` 有值就代表索引使用合理。
3. 把 `possible_keys` 当成应该强制使用的索引。
4. 认为 `key_len` 是索引文件大小。
5. 把 `rows` 当成最终返回行数。
6. 忽略 `filtered`，只看 rows。
7. 看到 `Using where` 就认为索引失效。
8. 把 `Using index` 和 `Using index condition` 当成同一件事。
9. 认为 `Using filesort` 一定写磁盘。
10. 认为 `Using temporary` 一定可以通过加索引消除。
11. 只看传统 EXPLAIN，不使用 `EXPLAIN ANALYZE` 验证估算。
12. 忽略 `loops`，低估 Nested Loop 内层总执行次数。
13. 机械按照 id 大小判断真实执行顺序。
14. 不考虑统计信息和数据倾斜，直接 `FORCE INDEX`。
15. 只用一个查询参数验证计划，没有覆盖热门值和冷门值。

### 面试话术

> MySQL 传统 EXPLAIN 有 12 个核心字段。先用 id 和 select_type 识别查询块，再看 table 的访问顺序；type 表示访问方式，重点区分 const、eq_ref、ref、range、index 和 ALL；possible_keys 是候选索引，key 是实际索引，key_len 用于判断联合索引使用前缀，ref 表示索引与常量还是前表列比较；rows 是预计检查行数，filtered 是预计过滤后保留比例，两者相乘可以近似得到传给下一步的行数；Extra 用来观察 Using index、Using index condition、Using filesort、Using temporary 等附加操作。传统 EXPLAIN 只有估算，最终要通过 EXPLAIN ANALYZE 比较 estimated rows、actual rows、actual time 和 loops。优化不能只追求某个 type 或消除某个 Extra，而要降低总扫描量、回表、排序、循环次数和实际耗时。

### 高频追问

- Q：`type=index` 是否表示进行了索引查找？
  A：不一定。它通常表示完整索引扫描，只是扫描索引而不是完整数据行，仍可能读取大量索引项。

- Q：`Using index` 是否表示 SQL 一定很快？
  A：不是。它只表示覆盖索引、无需回表。如果扫描了数百万个索引项，SQL 仍然可能很慢。

- Q：`Using index condition` 和 `Using index` 有什么区别？
  A：前者是索引条件下推，先在索引层过滤以减少回表，仍可能回表；后者通常表示覆盖索引，不需要读取完整数据行。

- Q：`rows=1` 是否代表最终只返回一行？
  A：不代表。它是当前迭代器每次扫描的估算值，还要结合 loops、filtered、连接和后续操作。

- Q：为什么 `possible_keys` 有索引而 `key=NULL`？
  A：优化器认为使用这些索引的成本高于全表扫描，例如选择性低、回表太多或需要读取大部分数据。

- Q：为什么 `possible_keys=NULL`，`key` 却可能有值？
  A：可能没有用于定位记录的索引，但优化器选择扫描一个更窄的覆盖索引，降低完整扫描成本。

- Q：`Using filesort` 是否一定使用磁盘？
  A：不是。filesort 是额外排序算法名称，小结果可能完全在内存中完成，大结果才可能产生临时文件。

- Q：如何判断优化器估算错误？
  A：使用 EXPLAIN ANALYZE 对比 estimated rows 与 actual rows。如果相差几个数量级，应检查统计信息、直方图、数据倾斜和联合索引。

- Q：连接查询为什么必须看 loops？
  A：Nested Loop 的内层算子会对外层每行执行一次。即使内层每次只返回几行，乘以数万次 loops 后总成本仍然很高。

## Q2：MySQL EXPLAIN 中 partitions 表示什么？索引条件下推如何工作？

### 背景

`partitions` 和 `Using index condition` 描述的是两个不同层级的优化：

- `partitions`：先做**分区裁剪**，确定需要访问哪些物理分区。
- `Using index condition`：进入选中的分区后，通过**索引条件下推（Index Condition Pushdown，ICP）**，在二级索引层提前过滤，减少回表。

一句话概括：

> `partitions` 解决“查哪些分区”，ICP 解决“扫描索引后，哪些记录值得回表”。

二者可以同时生效，但互不替代。`partitions` 只列出一个分区，不代表使用了索引；出现 `Using index condition`，也不代表只访问了少量分区。

### 一、partitions 字段与分区裁剪

#### 1. partitions 表示什么

对于分区表，传统 `EXPLAIN` 的 `partitions` 字段表示执行该查询时，优化器预计要访问的分区：

| 输出 | 含义 |
| --- | --- |
| `p2026h2` | 只访问 `p2026h2` |
| `p2025,p2026h1,p2026h2` | 访问列出的多个分区 |
| 所有分区 | 没有有效裁剪，或者查询确实需要所有分区 |
| `NULL` | 当前表不是分区表 |

分区裁剪（Partition Pruning）的核心是：优化器根据分区键条件，排除不可能包含目标数据的分区。

#### 2. 建表示例

~~~sql
CREATE TABLE order_archive (
    id BIGINT NOT NULL,
    created_at DATE NOT NULL,
    tenant_id BIGINT NOT NULL,
    status TINYINT NOT NULL,
    amount DECIMAL(12, 2) NOT NULL,
    -- 分区表达式中的 created_at 必须出现在每一个唯一键中
    PRIMARY KEY (id, created_at),
    KEY idx_tenant_status_amount (tenant_id, status, amount)
)
PARTITION BY RANGE COLUMNS(created_at) (
    PARTITION p2025 VALUES LESS THAN ('2026-01-01'),
    PARTITION p2026h1 VALUES LESS THAN ('2026-07-01'),
    PARTITION p2026h2 VALUES LESS THAN ('2027-01-01'),
    PARTITION pmax VALUES LESS THAN (MAXVALUE)
);
~~~

这里有一个重要限制：**分区表达式中使用的列，必须包含在表的每一个唯一键中，包括主键。** 因此主键不能只写成 `PRIMARY KEY (id)`。

#### 3. 分区裁剪示例

~~~sql
EXPLAIN
SELECT *
FROM order_archive
WHERE created_at >= '2026-07-01'
  AND created_at < '2027-01-01'
  AND tenant_id = 100;
~~~

代表性的执行计划会显示：

~~~text
partitions: p2026h2
~~~

优化器通过 `created_at` 的范围判断，确定数据只可能位于 `p2026h2`。如果去掉日期条件：

~~~sql
EXPLAIN
SELECT *
FROM order_archive
WHERE tenant_id = 100;
~~~

那么 `partitions` 通常会列出全部分区，因为 `tenant_id` 不能帮助判断数据位于哪个 `created_at` 分区。

#### 4. 裁剪之后仍然需要选择访问路径

MySQL 分区表的索引是分区内的本地索引。分区裁剪只是缩小物理数据范围，进入目标分区后，优化器仍要决定使用哪个索引、扫描多少索引项、是否回表。

~~~plantuml
@startuml
skinparam monochrome true
skinparam shadowing false

rectangle "WHERE created_at 范围" as condition
rectangle "分区裁剪" as pruning
rectangle "排除 p2025、p2026h1、pmax" as excluded
rectangle "访问 p2026h2" as selected
rectangle "选择分区内访问路径\n全扫或本地索引" as access

condition --> pruning
pruning --> excluded : 不可能命中
pruning --> selected : 可能命中
selected --> access
@enduml
~~~

因此下面两个判断都是错误的：

- `partitions=p2026h2`，所以一定走了索引。
- 查询使用了索引，所以一定发生了分区裁剪。

是否走索引应继续看 `type`、`key`、`rows` 和 `Extra`。

#### 5. 常见的裁剪不理想原因

1. `WHERE` 中没有分区键条件。
2. 条件范围本身跨越多个或全部分区。
3. `OR` 的某个分支无法限定分区，导致整体需要访问更多分区。
4. 对分区键进行复杂函数计算或隐式类型转换，优化器无法在执行前确定目标分区。
5. 分区设计和查询维度不一致，例如按日期分区，但主要查询只按租户过滤。

编写日期条件时，优先直接限定原始分区列：

~~~sql
-- 直接使用原始分区列和半开区间，边界清晰，也更容易进行范围裁剪
WHERE created_at >= '2026-07-01'
  AND created_at < '2027-01-01'
~~~

不要把“分区”理解成索引的替代品。分区主要用于数据管理和粗粒度裁剪；目标分区内仍可能需要合理索引。分区过多还会增加元数据、优化和打开分区的成本。

### 二、索引条件下推 ICP

#### 1. ICP 解决什么问题

InnoDB 使用二级索引查询完整行时，通常需要：

1. 扫描二级索引记录。
2. 取得记录中的主键值。
3. 根据主键到聚簇索引中读取完整行，即回表。
4. 对完整行执行剩余 `WHERE` 条件。

如果剩余条件中的列也位于当前二级索引中，ICP 可以将这部分判断下推给存储引擎：**先检查索引记录，满足条件后再回表。**

它不一定减少二级索引扫描量，但可以减少昂贵的回表次数。

~~~plantuml
@startuml
skinparam monochrome true
skinparam shadowing false

rectangle "扫描二级索引候选项" as scan

rectangle "未使用 ICP" as no_icp {
  rectangle "每个候选项都回表" as no_lookup
  rectangle "读取完整行后过滤" as no_filter
}

rectangle "使用 ICP" as icp {
  rectangle "先用索引列过滤" as idx_filter
  rectangle "通过后才回表" as yes_lookup
  rectangle "检查剩余条件" as remain_filter
}

scan --> no_lookup
no_lookup --> no_filter
scan --> idx_filter
idx_filter --> yes_lookup : 条件通过
idx_filter --> idx_filter : 条件不通过，继续扫描
yes_lookup --> remain_filter
@enduml
~~~

#### 2. 联合索引中的典型场景

已有索引：

~~~sql
KEY idx_tenant_status_amount (tenant_id, status, amount)
~~~

执行查询：

~~~sql
EXPLAIN
SELECT *
FROM order_archive
WHERE created_at >= '2026-07-01'
  AND created_at < '2027-01-01'
  -- tenant_id 的范围条件用于确定索引扫描区间
  AND tenant_id BETWEEN 100 AND 200
  -- status、amount 位于范围列之后，通常不能继续缩小扫描边界
  AND status = 9
  AND amount > 1000;
~~~

代表性结果可能是：

~~~text
partitions: p2026h2
type:       range
key:        idx_tenant_status_amount
Extra:      Using index condition; Using where
~~~

执行过程可以理解为：

1. 日期条件将访问范围裁剪到 `p2026h2`。
2. 使用 `tenant_id BETWEEN 100 AND 200` 确定联合索引的扫描区间。
3. `status`、`amount` 虽然通常不能继续缩小该范围的起止边界，但它们也在索引中。
4. 存储引擎通过 ICP 在索引记录上判断 `status = 9 AND amount > 1000`。
5. 只有通过判断的索引记录才根据主键回表。
6. Server 层继续检查不能下推的剩余条件，所以还可能显示 `Using where`。

注意：**“不能继续用于索引定位”不等于“这个索引列完全没用”。** 它仍可能通过 ICP 参与回表前过滤。

#### 3. ICP 的适用条件与限制

| 项目 | 说明 |
| --- | --- |
| 常见访问类型 | `range`、`ref`、`eq_ref`、`ref_or_null` |
| InnoDB 索引 | 主要作用于二级索引 |
| 聚簇索引 | 完整行已经在聚簇索引叶子节点，ICP 通常无法减少读取完整行的 I/O |
| 覆盖索引 | 已经无须回表，ICP 减少回表的价值很小 |
| 虚拟生成列 | InnoDB 虚拟生成列上的二级索引不支持 ICP |
| 子查询、存储函数 | 依赖子查询或存储函数的条件不能下推给存储引擎 |
| 分区表 | 可以与 InnoDB 分区表共同使用 |

ICP 一般在以下场景收益明显：

- 索引范围内候选记录较多。
- 下推条件能过滤掉大量候选记录。
- 查询需要读取索引之外的列，必须回表。
- 数据行较宽，或者回表存在较多随机 I/O。

以下场景收益通常有限：

- 已经是覆盖索引，无须回表。
- 索引定位非常精确，本来只有少量候选项。
- 下推条件选择性很差，绝大多数候选项仍需回表。

### 三、容易混淆的 Extra

| Extra | 核心含义 | 是否通常回表 |
| --- | --- | --- |
| `Using index` | 覆盖索引，仅从索引即可取得查询需要的数据 | 否 |
| `Using index condition` | 使用 ICP，在索引层先过滤，再对通过的记录回表 | 是 |
| `Using where` | 读取候选记录后仍需执行 `WHERE` 过滤 | 不确定 |

`Using index condition` 和 `Using index` 不是同义词：

- `Using index` 的重点是“索引已经覆盖查询，无需完整数据行”。
- `Using index condition` 的重点是“仍可能需要完整数据行，但先减少回表数量”。

`Using index condition; Using where` 同时出现也不矛盾：一部分条件由存储引擎在索引层判断，另一部分条件仍由 Server 层在读取完整行后判断。

### 四、如何验证 ICP 是否真的有收益

可以在同一会话、相同数据和相同参数下，对比关闭与开启 ICP 的实际执行情况：

~~~sql
-- 仅影响当前会话，先关闭 ICP 建立对照组
SET SESSION optimizer_switch = 'index_condition_pushdown=off';

EXPLAIN ANALYZE
SELECT *
FROM order_archive
WHERE created_at >= '2026-07-01'
  AND created_at < '2027-01-01'
  AND tenant_id BETWEEN 100 AND 200
  AND status = 9
  AND amount > 1000;

-- 恢复 ICP，再执行相同 SQL 进行比较
SET SESSION optimizer_switch = 'index_condition_pushdown=on';

EXPLAIN ANALYZE
SELECT *
FROM order_archive
WHERE created_at >= '2026-07-01'
  AND created_at < '2027-01-01'
  AND tenant_id BETWEEN 100 AND 200
  AND status = 9
  AND amount > 1000;
~~~

重点比较：

- `Extra` 是否出现 `Using index condition`。
- 实际耗时是否下降。
- 扫描候选记录与输出记录之间的差距。
- 冷热缓存下的结果是否稳定。

`EXPLAIN ANALYZE` 会真正执行 SQL，不要直接对高风险的 `UPDATE`、`DELETE` 使用，也不要在生产高峰对超大查询反复测试。

### 五、完整执行链路

把分区裁剪和 ICP 串起来，完整链路是：

~~~text
分区键条件
  -> 分区裁剪
  -> 访问选中的分区
  -> 在分区内选择二级索引
  -> 根据索引前缀确定扫描范围
  -> ICP 使用索引中的其他列过滤
  -> 只对通过的记录回表
  -> Server 层检查剩余 WHERE 条件
  -> 返回结果
~~~

优化时要分别回答三个问题：

1. 是否通过 `partitions` 把访问范围缩小到了合理分区？
2. `key` 和 `type` 是否说明分区内采用了合理的索引访问路径？
3. `Using index condition` 是否有效降低了回表成本？

### 常见误区

1. 看到 `partitions` 只有一个值，就认为查询一定很快。
2. 用分区代替索引，导致目标分区内仍然全扫描。
3. 看到联合索引范围列后的字段不能缩小扫描边界，就认为这些字段完全无法利用索引。
4. 把 `Using index condition` 当成覆盖索引。
5. 为了出现 ICP 而刻意调整 SQL；ICP 是降低回表成本的手段，不是优化目标本身。
6. 只看 `EXPLAIN` 标签，不使用 `EXPLAIN ANALYZE` 验证实际行数和耗时。

### 面试话术

> `EXPLAIN` 的 `partitions` 表示分区裁剪后计划访问的分区，它是物理范围层面的粗粒度过滤，不代表一定使用索引。进入目标分区后，优化器还会选择分区内的索引访问路径。索引条件下推 ICP 主要用于 InnoDB 二级索引：扫描索引时，如果部分 WHERE 条件只依赖索引中的列，存储引擎会先在索引记录上判断，通过后再回表，从而减少聚簇索引读取。执行计划中通常显示 `Using index condition`，它不同于表示覆盖索引的 `Using index`。二者结合时，先做分区裁剪，再做索引范围扫描和 ICP 过滤，最后回表并检查剩余条件。

### 高频追问

- Q：`partitions=p2026h2` 是否说明走了分区索引？
  A：不能。它只说明裁剪后访问 `p2026h2`，是否使用索引还要看 `type`、`key`、`rows` 和 `Extra`。

- Q：ICP 会减少索引扫描数量吗？
  A：不一定。ICP 经常仍要扫描相同的二级索引区间，但可以在索引层淘汰记录，减少后续回表数量。

- Q：为什么 InnoDB 的 ICP 主要用于二级索引？
  A：二级索引记录与完整数据行分离，先过滤可以减少到聚簇索引读取完整行的次数；聚簇索引叶子节点本身就是完整行，提前判断通常不能减少读取完整行的 I/O。

- Q：范围条件后的联合索引列一定失效吗？
  A：它们通常不能继续缩小索引扫描区间，但只要条件可下推且列位于索引中，仍可能通过 ICP 在回表前参与过滤。
