# MySQL 索引失效场景

## 问题索引

- Q1：为什么联合索引会因为最左前缀、范围查询或函数而失效？
- Q2：发现索引没有按预期使用时，应该如何验证和改写 SQL？

## Q1：为什么联合索引会因为最左前缀、范围查询或函数而失效？

**一句话结论：** B+Tree 索引依赖有序的联合键前缀；查询如果跳过前导列、破坏索引列的可比较形式，或扫描成本被优化器判断为不划算，就可能无法有效缩小扫描范围。

### 最左前缀

假设索引为 `(tenant_id, status, created_at)`，它的排序可以理解为：先按 `tenant_id`，同一租户内再按 `status`，最后按 `created_at`。因此：

- `WHERE tenant_id = ?` 可以使用前缀；
- `WHERE tenant_id = ? AND status = ?` 可以继续缩小范围；
- 跳过 `tenant_id` 直接按 `status` 查询，通常不能按该联合索引直接定位；
- 只查询 `tenant_id` 和 `created_at` 时，`created_at` 不能绕过中间列获得完整有序范围。

“失效”不是只有完全不用索引一种情况，也可能是只使用了前缀、扫描大量索引记录后再过滤，或者发生索引下推。必须结合 `EXPLAIN` 的 `key`、`key_len`、`rows`、`filtered` 和 `Extra` 判断实际效果。

### 范围查询后的列

在 `(a, b, c)` 中，如果 `a` 已经是范围条件，`b`、`c` 后续通常难以继续用作连续的精确定位条件；但它们仍可能参与索引条件下推或覆盖索引。不要把“后列不能继续缩小 B+Tree 范围”误解为“后列完全没有任何作用”。

### 对索引列做函数或运算

```sql
-- 可能使普通索引难以直接定位
WHERE DATE(created_at) = '2026-08-14'
WHERE amount + 1 = 100

-- 改写为对列本身做范围匹配
WHERE created_at >= '2026-08-14 00:00:00'
  AND created_at <  '2026-08-15 00:00:00'
WHERE amount = 99
```

改写的本质是把计算从索引列上移开，让数据库可以直接比较索引中保存的原始值。若业务必须按表达式查询，也可以评估生成列或函数索引，但要结合版本、写入成本和维护复杂度。

## Q2：发现索引没有按预期使用时，应该如何验证和改写 SQL？

**一句话结论：** 先用执行计划和真实数据分布确认问题，再区分语法导致的不可用、统计信息不准、选择性不足和成本判断，最后用等价 SQL、索引调整或数据模型改造验证收益。

### 排查顺序

1. 用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 对比预估行数与实际行数。
2. 检查 `possible_keys`、`key`、`key_len`、`rows`、`filtered` 和 `Extra`。
3. 判断是否存在隐式类型转换、前导 `%`、函数包列、`OR` 分支、负向条件或不稳定排序。
4. 检查列的选择性、数据倾斜、统计信息和索引是否过期。
5. 用等价范围条件、`UNION ALL` 拆分或覆盖索引做低风险实验。
6. 在代表性数据量和真实参数上比较执行时间、扫描行数、锁范围和资源消耗。

### 不能只看“用了索引”

优化器可能选择全表扫描，因为结果集占比很大，顺序读取比随机回表更便宜；也可能使用了索引，但扫描行数远超返回行数，仍然是低效计划。索引优化的目标是减少无效扫描和回表，而不是让 `key` 字段非空。

### 面试追问

- Q：`LIKE 'abc%'` 和 `LIKE '%abc'` 有什么区别？
  A：前者有明确的左侧前缀，通常可以形成范围；后者需要从任意位置匹配，普通 B+Tree 难以直接定位。
- Q：为什么 `OR` 有时导致索引失效？
  A：不同分支的选择性和索引能力不一致时，合并多个访问路径的成本可能高于全表扫描；可以拆成多个可优化分支并用 `UNION ALL` 验证。
