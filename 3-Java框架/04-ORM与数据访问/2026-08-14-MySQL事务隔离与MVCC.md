# MySQL 事务隔离与 MVCC

## 问题索引

- Q1：MySQL 的事务隔离级别、ReadView 和 MVCC 如何配合？
- Q2：MVCC 能解决幻读吗？什么时候还需要锁？

## Q1：MySQL 的事务隔离级别、ReadView 和 MVCC 如何配合？

**一句话结论：** InnoDB 通过 Undo 版本链保存历史版本，ReadView 根据事务可见性规则选择一个版本；MVCC 主要让普通一致性读少加锁，但不等于所有读写都无锁。

### 版本链

更新记录时，旧版本写入 Undo，当前记录保留最新版本，并通过回滚指针连接历史版本。事务读取时沿版本链查找第一个对自己可见的版本。

```text
当前记录 trx_id = T3
        |
        v
Undo 版本 T2 -> Undo 版本 T1
```

ReadView 会依据创建时活跃事务集合、最小事务 ID 和下一个待分配事务 ID 判断版本是否可见。不同隔离级别的关键差异在于 ReadView 创建时机：

- RC：通常每次一致性读创建新的 ReadView，能读到其他事务已提交的新版本。
- RR：通常第一次一致性读创建 ReadView，后续一致性读复用它，因此同一事务内更稳定。
- 当前读：`SELECT ... FOR UPDATE`、`UPDATE` 等读取最新版本，并通过锁保护后续修改。

## Q2：MVCC 能解决幻读吗？什么时候还需要锁？

**一句话结论：** MVCC 能让快照读在事务内保持一致，但不能替代当前读的范围保护；RR 下 InnoDB 还会通过间隙锁和临键锁抑制范围内的并发插入。

### 快照读与当前读

| 读类型 | 典型语句 | 主要机制 |
| --- | --- | --- |
| 快照读 | 普通 `SELECT` | ReadView + Undo 版本链 |
| 当前读 | `SELECT ... FOR UPDATE` | 读取最新版本并加锁 |
| 修改语句 | `UPDATE`、`DELETE` | 当前读 + 记录/范围锁 |

如果业务流程是“查询可用库存 -> 决定扣减”，仅靠快照读不能阻止其他事务插入或修改。需要把判断和修改设计成当前读、条件更新或带版本号的原子操作。

### 常见误区

- “RR 绝对没有幻读”过于绝对，要区分快照读和当前读。
- “MVCC 不加锁”不准确；更新、当前读和索引范围访问仍可能加锁。
- 隔离级别不能替代业务幂等、唯一约束和状态机。
