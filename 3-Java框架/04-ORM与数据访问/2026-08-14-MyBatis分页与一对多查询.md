# MyBatis 分页与一对多查询

## 问题索引

- Q1：一对多查询为什么不能直接对 JOIN 结果分页？如何设计？
- Q2：分页插件应该放在哪一层？如何避免 count、排序和重复数据问题？

## Q1：一对多查询为什么不能直接对 JOIN 结果分页？如何设计？

**一句话结论：** 一对多关系分页的对象通常是“主表记录”，而 `JOIN` 后分页的对象变成了“关联行”；应先分页得到主表 ID，再批量查询主表和子表，最后在内存中组装结果。

### 背景

例如一个订单有多条明细，页面要求“每页 20 个订单，并展示每个订单的明细”。如果直接执行：

```sql
SELECT o.id, o.order_no, i.sku_id, i.quantity
FROM orders o
LEFT JOIN order_items i ON i.order_id = o.id
ORDER BY o.id DESC
LIMIT 0, 20;
```

数据库会先产生订单与明细的关联行，再对关联行执行 `LIMIT`。一个订单占用多行后，20 行可能只包含几个订单，页面的“20 条”就不再是 20 个主表对象。

### 推荐流程

```text
查询主表条件
  -> 统计主表总数
  -> 按稳定排序查询本页主表 ID
  -> 用 IN 批量查询主表
  -> 用 IN 批量查询子表
  -> 按主表 ID 分组组装
  -> 按第一页 ID 顺序返回
```

第一步只对主表分页：

```sql
SELECT o.id, o.order_no, o.created_at
FROM orders o
WHERE o.user_id = #{userId}
ORDER BY o.created_at DESC, o.id DESC
LIMIT #{offset}, #{pageSize};
```

第二步用本页 ID 批量查明细：

```sql
SELECT i.order_id, i.sku_id, i.quantity
FROM order_items i
WHERE i.order_id IN (...)
ORDER BY i.order_id, i.id;
```

应用层组装时要使用 `order_id -> List<Item>` 的映射，并按第一步得到的主表顺序返回。不能依赖 `IN` 查询天然保持传入 ID 的顺序。

### 为什么这是两个查询而不是一次查询

- **分页语义正确：** `LIMIT` 作用于订单，而不是订单明细行。
- **避免笛卡尔放大：** 多个一对多关系同时 JOIN 时，行数会相乘。
- **便于控制查询成本：** 子表只查询当前页的主键集合。
- **边界更明确：** 主表的权限、排序、总数和子表加载策略可以分别验证。

如果只需要判断是否存在子表、统计数量或返回汇总字段，可以使用 `EXISTS`、聚合或预计算字段，不必把所有明细 JOIN 出来。

### 一致性与性能边界

- 两次查询之间如果允许数据变化，主表和明细可能来自不同时间点；强一致要求下应使用合适的事务隔离级别，或者接受列表页的最终一致性。
- `IN` 列表不能无限增长。页大小过大时应分批查询，或者使用临时表、批量接口。
- 排序必须稳定，建议使用 `created_at + id` 这样的联合排序，避免同一时间戳下翻页重复或遗漏。
- 深分页的 `OFFSET` 越来越昂贵时，可改为基于最后一条记录的游标分页：`WHERE (created_at, id) < (...)`。

## Q2：分页插件应该放在哪一层？如何避免 count、排序和重复数据问题？

**一句话结论：** 分页插件只能负责改写明确的主表查询，不能替业务决定一对多的返回语义；使用前要检查 count SQL、排序字段、插件顺序和多数据源边界。

### 插件的职责边界

PageHelper 等分页插件通常拦截 `Executor` 查询，在执行前追加数据库方言对应的分页语句，并可能生成 count 查询。它适合解决“单条主查询分页”，不适合把任意复杂 JOIN 自动变成正确的一对多分页。

推荐把职责拆开：

1. Service 明确本页对象是订单还是订单明细。
2. Mapper 的主查询只返回可分页的主表结果或主表 ID。
3. 插件对这条主查询做分页。
4. Service 根据结果批量加载关联数据。
5. 返回前恢复主表顺序并补齐空集合，避免前端出现 `null` 与 `[]` 混用。

### 常见坑

| 问题 | 根因 | 处理方式 |
| --- | --- | --- |
| 总数明显偏大 | count 对 JOIN 行计数 | 对主表主键 `COUNT(DISTINCT id)`，或单独写主表 count |
| 每页数量不稳定 | 排序不稳定或直接对关联行分页 | 使用唯一键补充排序，先分页主表 |
| 分页失效 | 分页参数未绑定当前线程或查询未经过插件 | 检查调用顺序、数据源和代理链 |
| 多次分页叠加 | 嵌套调用或插件重复注册 | 明确分页边界，统一插件配置 |
| SQL 改写出错 | 方言、子查询、注释或复杂 SQL 不兼容 | 对关键 SQL 做集成测试，必要时手写分页 |

### 面试追问

- Q：为什么不直接使用 MyBatis 的嵌套查询？
  A：嵌套查询容易产生 N+1；可以用批量查询或一次性结果映射，但必须验证 SQL 数量、分页语义和内存占用。
- Q：一对多结果映射会不会重复主对象？
  A：正确配置主键列和 `resultMap` 的 `<id>` 后，MyBatis 可以按主键合并结果；但 JOIN 结果仍然先被放大，分页与内存成本问题不会因此消失。
