# 深分页成本分析与解决方案

## 问题索引

- Q1：深分页为什么成本高？如何分析并选择解决方案？

## Q1：深分页为什么成本高？如何分析并选择解决方案？

### 背景

常见分页 SQL 是：

```sql
SELECT id, order_no, user_id, status, create_time
FROM orders
WHERE tenant_id = ?
ORDER BY create_time DESC, id DESC
LIMIT 1000000, 20;
```

前几页可能很快，但页码越深，查询延迟越高。根本原因不是 `LIMIT` 返回了 20 行，而是数据库通常需要先定位、扫描或排序前面的 `offset` 行，再丢弃它们，最后返回 `pageSize` 行。

### 核心原理

#### 1. 深分页的成本模型

```text
扫描/排序成本 ≈ offset + pageSize
返回数据量    ≈ pageSize
```

当排序字段没有可用索引时，数据库可能需要：

```text
过滤 -> 扫描大量记录 -> filesort/临时表 -> 丢弃 offset 行 -> 返回 pageSize 行
```

即使有索引，也不代表深分页是 O(1)：

- B+Tree 可以快速找到索引范围，但仍要顺序遍历 offset 个索引项。
- 如果查询列不在二级索引中，每个候选项还可能回表读取聚簇记录。
- offset 很大时，回表的随机 I/O、CPU 和 Buffer Pool 压力都会放大。
- 每次翻页都重新从索引起点走到 offset，页码之间不会自动复用上一次扫描结果。

所以“加了索引”通常只能解决过滤和排序，不能让 `LIMIT 1000000,20` 自动变成常数成本。

#### 2. 需要先看执行计划

```sql
EXPLAIN ANALYZE
SELECT id, order_no, user_id, status, create_time
FROM orders
WHERE tenant_id = 10
ORDER BY create_time DESC, id DESC
LIMIT 1000000, 20;
```

重点观察：

| 指标 | 关注点 |
| --- | --- |
| `key` | 是否使用了覆盖过滤和排序的联合索引 |
| `rows` / 实际扫描行数 | 是否远大于最终返回的 20 行 |
| `Extra` | 是否出现 filesort、temporary 或回表迹象 |
| 实际耗时 | 深页是否明显高于第一页 |
| 服务器指标 | CPU、磁盘读取、Buffer Pool 命中率、锁等待、连接池等待 |

需要对第一页、中间页、深页分别压测，不能只用第一页的执行计划判断分页方案是否可行。

#### 3. 数据变化还会造成分页不稳定

只使用 `ORDER BY create_time DESC` 可能有两个问题：

- `create_time` 相同的记录没有确定顺序，页边界可能变化。
- 翻页期间有新增或删除记录，offset 会整体偏移，导致重复或漏数据。

因此分页排序至少需要一个唯一且稳定的 tie-breaker，例如：

```sql
ORDER BY create_time DESC, id DESC
```

其中 `id` 不是为了让查询更快，而是为了让排序顺序确定。真正的性能仍依赖与过滤条件匹配的联合索引。

### 业务场景

分页方式应由用户行为和业务目标决定：

| 场景 | 目标 | 适合方案 |
| --- | --- | --- |
| 移动端、后台列表连续向下翻页 | 快速拿下一页 | Keyset/Seek 游标分页 |
| 运营人员偶尔跳到某个中等页码 | 兼顾实现成本和查询速度 | 覆盖索引 + 延迟回表，限制最大页码 |
| 导出全部订单 | 长时间稳定读取 | 异步导出、分段游标、快照或离线任务 |
| 搜索结果深翻页 | 依赖排序和检索引擎 | Elasticsearch `search_after` + PIT 等游标方案 |
| 必须精确跳到任意页 | 保持页码语义 | 预计算页边界、物化 ID 快照或接受更高成本 |

### 解决方案

#### 1. 首选：Keyset/Seek 游标分页

第一次查询：

```sql
-- 联合索引要覆盖租户过滤、排序字段和唯一 tie-breaker。
CREATE INDEX idx_orders_tenant_time_id
    ON orders (tenant_id, create_time, id);

SELECT id, order_no, user_id, status, create_time
FROM orders
WHERE tenant_id = 10
ORDER BY create_time DESC, id DESC
LIMIT 20;
```

返回下一页游标时，保存本页最后一条记录的 `(create_time, id)`。下一页使用：

```sql
SELECT id, order_no, user_id, status, create_time
FROM orders
WHERE tenant_id = 10
  AND (
      create_time < '2026-08-12 10:00:00'
      OR (create_time = '2026-08-12 10:00:00' AND id < 987654)
  )
ORDER BY create_time DESC, id DESC
LIMIT 20;
```

它把“跳过前面一百万行”改成“从上一次边界继续向后扫描”，每页成本主要与 pageSize 相关。

游标接口示意：

```java
public PageResult<Order> nextPage(Long tenantId, Cursor cursor, int pageSize) {
    // 游标包含最后一条记录的稳定排序字段，不能只保存非唯一的 createTime。
    int safeSize = Math.min(pageSize, 100);
    List<Order> rows = orderMapper.selectAfter(
        tenantId,
        cursor == null ? null : cursor.createTime(),
        cursor == null ? null : cursor.id(),
        safeSize + 1 // 多查一条，用于判断是否还有下一页
    );

    boolean hasNext = rows.size() > safeSize;
    if (hasNext) {
        rows.remove(rows.size() - 1); // 不把探测行返回给调用方
    }

    Cursor next = rows.isEmpty()
        ? null
        : Cursor.of(rows.get(rows.size() - 1).getCreateTime(), rows.get(rows.size() - 1).getId());
    return new PageResult<>(rows, next, hasNext);
}
```

对外暴露的游标应编码并签名，避免调用方篡改租户、排序字段或查询条件。游标还应绑定过滤条件版本，防止用户把一个列表的游标用于另一个查询。

#### 2. 联合索引与覆盖索引

索引设计要匹配真实查询：

```text
等值过滤列 -> 排序列 -> 唯一 tie-breaker -> 必要时覆盖列
```

例如：

```sql
CREATE INDEX idx_orders_tenant_time_id
    ON orders (tenant_id, create_time, id);
```

不要为了避免回表把所有业务字段都塞进索引。覆盖索引可以减少回表，但会增加索引体积、写放大和缓存压力，应通过执行计划和压测确认收益。

#### 3. 延迟回表：适合有限深度的随机跳页

如果产品必须保留页码跳转，可以先在较窄的覆盖索引中取出主键，再回表取完整行：

```sql
SELECT o.id, o.order_no, o.user_id, o.status, o.create_time
FROM orders AS o
JOIN (
    SELECT id
    FROM orders
    WHERE tenant_id = 10
    ORDER BY create_time DESC, id DESC
    LIMIT 100000, 20
) AS page_ids ON page_ids.id = o.id
ORDER BY o.create_time DESC, o.id DESC;
```

它减少了前面大量记录的宽行回表成本，但子查询仍然要扫描 offset，因此不能解决无限深分页。实践中应配合最大页码、最大 offset 和异步导出限制。

#### 4. 预计算边界或物化 ID 快照

对运营报表、审计查询等必须随机跳页的场景，可以在查询开始时生成查询快照：

```text
筛选条件 -> 生成有序 ID 列表/页边界 -> 保存 snapshotId
用户跳页 -> 根据 snapshotId 读取对应 ID 段 -> 批量回表
```

优点是页码稳定，缺点是需要额外存储、快照过期策略和生成成本。数据量很大时应转成异步任务或离线文件，不要让在线请求同步生成百万级 ID 快照。

#### 5. 搜索引擎和导出场景

在 Elasticsearch 中，深翻页不应无限增大 `from + size`。连续读取可使用 `search_after`，需要跨多次请求保持一致视图时配合 PIT；全量导出可使用 scroll 或离线任务，具体方式要根据版本和访问模式选择。

数据库全量导出同样优先使用按主键/业务时间的游标分段读取，分批写入文件，并限制导出任务并发，避免把在线查询资源耗尽。

#### 6. 限制 pageSize 与 count 成本

- 设置合理的最大 `pageSize`，例如 100 或 500，拒绝任意超大值。
- 对深页设置最大页码，超过后提示使用筛选条件、游标或导出。
- `COUNT(*)` 不要和每一页查询强绑定；可以使用缓存、近似值或异步统计。
- 对没有唯一排序键、没有选择性过滤条件的查询，先要求用户补充筛选条件。

### 踩坑点

- 只加 `LIMIT` 语法或只使用 PageHelper，并不能消除 offset 扫描成本；分页插件最终通常仍会生成 offset 分页 SQL。
- 只按时间排序，不加唯一 ID，可能出现重复和漏数据。
- 把 `id > lastId` 直接套到按 `create_time` 排序的查询上，排序条件不一致时结果会错误。
- 联合索引列顺序不匹配过滤和排序，可能仍然 filesort 或扫描大量无关记录。
- 覆盖索引字段过多，导致索引膨胀、写入变慢和 Buffer Pool 被挤占。
- 延迟回表可以降低回表成本，但无法把随机跳到第 100000 页变成 O(1)。
- 把“总页数”当成必须实时精确的数据，导致每次列表请求都执行昂贵 count。
- 游标没有绑定筛选条件，用户切换租户、状态或时间范围后继续使用旧游标。
- 数据频繁更新时没有明确一致性语义：是接受实时列表变化，还是需要快照视图。

## 面试追问

- Q：为什么有索引后 `LIMIT 1000000,20` 仍然慢？
  A：索引能帮助定位过滤和排序范围，但数据库通常仍需顺序扫描并跳过前 1000000 个索引项；非覆盖索引还会产生大量回表，所以成本仍随 offset 增长。

- Q：游标分页为什么需要 `(create_time,id)` 两个字段？
  A：时间可能相同，单独用时间无法确定页边界；加入唯一 ID 后可以构造严格的字典序条件，避免重复或漏数据。

- Q：游标分页能不能跳到第 100 页？
  A：天然适合连续下一页，不适合任意页码跳转。若必须跳页，可用页边界快照、物化 ID、延迟回表并限制深度，或改变产品交互为筛选和游标。

- Q：深分页优化是否一定要换成 Elasticsearch？
  A：不一定。订单列表等结构化查询优先用数据库联合索引和 Seek 分页；复杂检索、相关性排序和大范围搜索才考虑搜索引擎，导出则优先异步任务。
