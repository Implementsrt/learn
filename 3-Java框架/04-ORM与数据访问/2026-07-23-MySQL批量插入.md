# MySQL 批量插入

## 问题索引

- Q1：MySQL 批量插入有哪些方式，如何选择和优化？

## Q1：MySQL 批量插入有哪些方式，如何选择和优化？

### 核心结论

批量插入的主要目标是减少：

- 应用与数据库之间的网络往返。
- SQL 解析和执行次数。
- 事务提交及 redo/binlog 刷盘次数。

常用方案按数据规模和来源选择：

| 方案 | 典型用途 | 特点 |
| --- | --- | --- |
| 多值 INSERT | 几十到几千行的普通业务批量写入 | 一条 SQL 携带多行 VALUES，简单高效 |
| JDBC Batch | SQL 结构相同、分批绑定参数 | 驱动可重写为多值 INSERT，适合通用批处理 |
| MyBatis `ExecutorType.BATCH` | MyBatis 中重复执行相同 Mapper 写方法 | 底层使用 JDBC Batch，需要主动 flush |
| `LOAD DATA [LOCAL] INFILE` | CSV 等大文件、高吞吐离线导入 | 通常最快，但需要文件、安全和权限治理 |

不要用一个包含几十万行的超大 SQL。正确做法是**分批、短事务、可重试、可观测**。

### 四种方式的执行关系

~~~plantuml
@startuml
skinparam monochrome true
skinparam shadowing false

actor App
component "MyBatis/JDBC" as Client
component "SQL 或 JDBC Batch" as Batch
database "MySQL Server" as MySQL

App -> Client : 提交一批数据
Client -> Batch : 多值 INSERT\n或 addBatch
Batch -> MySQL : 减少网络往返
MySQL -> MySQL : 约束检查/索引维护
MySQL -> MySQL : redo/undo/binlog
MySQL --> App : 影响行数/异常
@enduml
~~~

性能提升并不是“数据库一次写入不需要逐行处理”，而是把网络、解析、提交等固定成本摊到更多行上。MySQL 仍需逐行检查唯一约束、外键并维护索引。

### 方式一：多值 INSERT

SQL 形式：

~~~sql
INSERT INTO sys_user (id, username, mobile, created_at)
VALUES
    (?, ?, ?, ?),
    (?, ?, ?, ?),
    (?, ?, ?, ?);
~~~

MyBatis XML 常用 `<foreach>` 生成：

~~~xml
<insert id="insertBatch">
    INSERT INTO sys_user (id, username, mobile, created_at)
    VALUES
    <foreach collection="users" item="user" separator=",">
        (
            #{user.id},
            #{user.username},
            #{user.mobile},
            #{user.createdAt}
        )
    </foreach>
</insert>
~~~

这是**一条多值 SQL**，不是 JDBC Batch。它本身不依赖 `rewriteBatchedStatements=true` 才能合并。

优点：

- 实现简单。
- 网络往返和 SQL 解析次数少。
- 一批数据作为一条语句，原子性直观。

限制：

- SQL 和参数数量随行数增长。
- 受 `max_allowed_packet`、驱动报文、SQL 长度和内存影响。
- 单条语句失败时整批失败，不容易直接定位坏数据。
- 一次插入过多行会产生较大的 redo、binlog 和复制延迟。

单批大小没有通用固定值。普通窄表可以从 200～1000 行开始压测，同时限制单批字节数；宽表、JSON/BLOB 或大量索引表应显著减小。

### 方式二：JDBC Batch

JDBC Batch 对同一个 `PreparedStatement` 重复绑定参数：

~~~java
String sql = "INSERT INTO sys_user "
    + "(id, username, mobile, created_at) VALUES (?, ?, ?, ?)";

try (Connection connection = dataSource.getConnection()) {
    connection.setAutoCommit(false);

    try (PreparedStatement statement = connection.prepareStatement(sql)) {
        int batchSize = 500;
        int pendingCount = 0;
        for (int i = 0; i < users.size(); i++) {
            User user = users.get(i);
            statement.setLong(1, user.getId());
            statement.setString(2, user.getUsername());
            statement.setString(3, user.getMobile());
            statement.setTimestamp(4, Timestamp.valueOf(user.getCreatedAt()));
            statement.addBatch();
            pendingCount++;

            if (pendingCount == batchSize) {
                // 定期发送并提交，避免客户端和数据库事务无限增长。
                statement.executeBatch();
                statement.clearBatch();
                connection.commit();
                pendingCount = 0;
            }
        }

        // 提交不足一个完整批次的尾部数据。
        if (pendingCount > 0) {
            statement.executeBatch();
            statement.clearBatch();
            connection.commit();
        }
    } catch (SQLException ex) {
        // 显式回滚当前尚未提交的批次；之前已提交批次需要依靠任务幂等重试。
        connection.rollback();
        throw ex;
    }
} catch (SQLException ex) {
    // 生产代码还应记录失败批次范围，并根据错误类型决定是否重试。
    throw new IllegalStateException("batch insert failed", ex);
}
~~~

MySQL Connector/J 常用连接参数：

~~~text
jdbc:mysql://host:3306/app?rewriteBatchedStatements=true
~~~

它可以把符合条件的重复 INSERT Batch 重写成多值 INSERT，减少服务端执行和网络交互。

需要准确区分：

- `<foreach>` 已经生成一条多值 INSERT，通常不依赖这个参数。
- `PreparedStatement#addBatch` 或 MyBatis `BatchExecutor` 才属于 JDBC Batch，参数才可能产生明显收益。
- 驱动是否重写还受 SQL 形式、驱动版本和语句类型限制，应通过驱动日志、抓包或实际压测验证。

### 方式三：MyBatis BatchExecutor

MyBatis 可以通过 `ExecutorType.BATCH` 累积相同 SQL 的多次更新：

~~~java
try (SqlSession session = sqlSessionFactory.openSession(ExecutorType.BATCH, false)) {
    UserMapper mapper = session.getMapper(UserMapper.class);
    int batchSize = 500;

    for (int i = 0; i < users.size(); i++) {
        mapper.insertOne(users.get(i));

        if ((i + 1) % batchSize == 0) {
            // flushStatements 才真正触发当前批次的 JDBC Batch。
            session.flushStatements();
            session.commit();
            // 防止一级缓存和批处理对象长期占用内存。
            session.clearCache();
        }
    }

    session.flushStatements();
    session.commit();
}
~~~

在 Spring 中应通过受 Spring 管理且配置为 BATCH 的 `SqlSessionTemplate` 使用，并让 `@Transactional` 管理事务。不要在已有 Spring 事务中随意手动 `openSession()`，否则可能脱离当前事务连接。

`BatchExecutor` 的注意点：

- 未 `flushStatements()` 前，数据库可能还没有真正执行。
- 单条更新返回值可能是批处理占位值，不能当作最终影响行数。
- 中途执行查询会触发批处理 flush，影响批次边界。
- 批次过大会占用应用堆、驱动缓冲、数据库事务和日志空间。
- 发生 `BatchUpdateException` 时，要结合 update counts 和事务回滚策略定位失败范围。

### 方式四：LOAD DATA

大规模文件导入可以使用：

~~~sql
LOAD DATA LOCAL INFILE '/path/users.csv'
INTO TABLE sys_user
FIELDS TERMINATED BY ','
OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\n'
IGNORE 1 LINES
(id, username, mobile, created_at);
~~~

它减少逐条 SQL 解析和应用层对象构造，通常适合百万级 CSV 导入。

需要治理：

- `LOCAL INFILE` 是否被客户端和服务端允许。
- 文件来源、路径和内容安全。
- 字符集、转义、换行符、NULL 和日期格式。
- 错误行处理和导入结果校验。
- 大事务、binlog、复制延迟和磁盘空间。
- 先落临时表校验，再合并到正式表。

在线交易接口通常不直接使用 LOAD DATA；离线导入任务可以采用“对象存储文件 -> 临时表 -> 校验 -> 正式表”的流程。

### 分批和事务怎么设计

批次大小应同时控制“行数”和“字节数”：

~~~text
达到 500 行
或
累计参数/SQL 接近 1～5 MB
  -> flush + commit
~~~

这里的数字只是起始压测值，不是数据库标准。最终要看：

- 单行平均大小和最大大小。
- 二级索引和唯一索引数量。
- redo、binlog 和磁盘吞吐。
- 主从复制延迟。
- 应用堆和驱动内存。
- 锁等待、接口 P99 和失败重试成本。

一个超大事务会导致：

- undo/redo 和 binlog 快速增长。
- 锁持有时间变长。
- 主从复制出现大事务延迟。
- 回滚时间长。
- 失败后重试成本高。

如果业务要求整份文件全有或全无，而数据规模很大，通常先导入任务表或临时表，校验完成后通过状态切换发布结果，而不是用一个百万行数据库事务硬扛原子性。

### 索引、约束和表结构的影响

每插入一行，MySQL 都可能维护：

- 聚簇索引。
- 多个二级索引。
- 唯一约束。
- 外键约束。
- 生成列和触发器。

优化原则：

- 删除无用重复索引，而不是为导入临时禁用必要约束。
- 数据尽量按聚簇主键有序写入，减少随机页分裂。
- 使用应用生成的全局 ID 时，考虑 ID 的趋势递增性。
- 批量导入前评估触发器和级联外键成本。
- 不要为了速度关闭唯一约束后忘记做重复校验。

InnoDB 二级索引不是“最后统一更新”，批量插入过程中仍需要维护。批量方式主要减少固定开销，不会让索引维护消失。

### 幂等和重复数据处理

批处理经常因超时、网络中断和任务重跑发生重复提交。应使用业务唯一键保证幂等。

常见语法：

~~~sql
INSERT INTO sys_user (id, external_no, username)
VALUES (?, ?, ?) AS new
ON DUPLICATE KEY UPDATE
    username = new.username;
~~~

注意：

- `INSERT IGNORE` 会忽略部分可转换的错误和重复键，容易隐藏脏数据，不应无差别使用。
- `ON DUPLICATE KEY UPDATE` 会触发更新逻辑，要评估 binlog、更新时间和影响行数语义。
- 较新 MySQL 已不推荐使用 `VALUES(username)` 引用待插入值，优先使用上面的新行别名。
- 最可靠的幂等基础是明确的业务唯一键，而不是先查询再插入。
- 失败重试应按批次记录边界、任务 ID 和幂等键。

### 自增主键和回填 ID

批量插入后为每个对象回填自增 ID 依赖驱动、SQL 形式和 MyBatis 配置，复杂批次中容易出现兼容性问题。

推荐：

- 需要稳定关联时，在应用侧提前生成 Snowflake、号段或 UUIDv7 等 ID。
- 必须使用自增 ID 时，对当前 Connector/J 和 MyBatis 版本做集成测试。
- 不要通过“首个 generated key + 行号”推算所有 ID，存在并发、自增步长和配置差异风险。

### 分库分表场景

批量数据包含多个分片键时，应先按目标分片分组：

~~~text
输入数据
  -> 计算 merchant_code/user_id 对应分片
  -> 按 dataSource + physicalTable 分组
  -> 每个目标节点独立分批插入
  -> 汇总成功和失败结果
~~~

不要把跨多个分片的数据拼成一个逻辑大批次并期待 ShardingSphere 始终高效拆分。需要限制并发分片数、每分片批次大小和总连接数，避免一次任务同时占满所有数据库连接池。

### 常见误区

1. 把 MyBatis `<foreach>` 多值 INSERT 与 `ExecutorType.BATCH` 当成同一种机制。
2. 认为 `<foreach>` 必须配置 `rewriteBatchedStatements=true` 才会合并 SQL。
3. 一次拼接几万行 SQL，导致报文过大、解析慢或 OOM。
4. 一个事务导入全部数据，失败后长时间回滚。
5. 只看应用耗时，不看 redo、binlog、复制延迟和磁盘 IO。
6. 使用 `INSERT IGNORE` 掩盖数据格式和约束问题。
7. BatchExecutor 不主动 flush，误以为 Mapper 调用已经入库。
8. 批量插入跨多个分片，却不先按分片键分组。
9. 依赖批量自增 ID 推算，没有做驱动版本集成测试。
10. 导入任务和在线交易共用连接池、线程池，没有资源隔离。

### 面试话术

> MySQL 批量插入的核心是减少网络往返、SQL 解析和事务提交次数。普通业务批量写可以用多值 INSERT，MyBatis 用 foreach 直接生成一条 SQL；大量同构语句可以使用 JDBC Batch 或 MyBatis BatchExecutor，并在 Connector/J 中评估 rewriteBatchedStatements，让驱动把重复 INSERT 重写成多值语句。需要注意 foreach 本身已经是一条 SQL，不依赖这个参数。批次不能无限大，我通常按行数和字节数双重切分，从 200～1000 行开始压测，并控制事务、redo、binlog、复制延迟和内存。百万级文件导入可用 LOAD DATA 进入临时表后校验发布。批处理必须通过业务唯一键保证幂等，分库分表场景先按分片键分组，再对每个目标节点独立批量写入。

### 高频追问

- Q：`foreach` 与 BatchExecutor 有什么区别？
  A：`foreach` 在客户端生成一条包含多组 VALUES 的 SQL；BatchExecutor 累积多次 Mapper 更新，最终调用 JDBC Batch。

- Q：为什么不能一次插入十万行？
  A：会放大 SQL 报文、内存、事务日志、锁时间、复制延迟和失败回滚成本，应分批提交。

- Q：批次大小设置多少？
  A：没有固定答案。窄表可从 200～1000 行开始，并同时限制字节数，通过吞吐、P99、redo、binlog 和复制延迟压测调整。

- Q：批量插入怎么保证幂等？
  A：建立业务唯一键，结合 upsert 或重复键分类处理，并记录任务与批次状态，不能只靠“插入前先查”。

- Q：批量插入为什么会拖慢主从复制？
  A：大事务会生成大量 binlog，从库通常要完整接收并应用后才推进位点，容易形成复制延迟。
