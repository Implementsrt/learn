# MyBatis 插件与数据权限

## 问题索引

- Q1：MyBatis 插件（Interceptor）是如何工作的？
- Q2：如何用 MyBatis 插件实现低侵入数据权限？

## Q1：MyBatis 插件（Interceptor）是如何工作的？

**一句话结论：** MyBatis 在创建四大核心对象时通过插件链包装目标对象，插件拦截指定方法后可以读取上下文、改写参数或 SQL，再决定是否继续执行。

### 核心原理

MyBatis 官方插件可拦截的对象主要包括：

- `Executor`：执行器，适合统一记录 SQL、分页或执行耗时。
- `StatementHandler`：语句处理器，适合改写 SQL 和处理参数。
- `ParameterHandler`：参数处理器，适合统一参数注入。
- `ResultSetHandler`：结果集处理器，适合统一结果转换。

插件通过 JDK 动态代理包裹目标对象。调用链可以概括为：

```text
Configuration 创建核心对象
  -> InterceptorChain.pluginAll()
  -> Plugin.wrap() 生成代理
  -> 业务调用 Mapper
  -> 代理判断方法签名是否匹配
  -> 拦截器处理或继续调用目标对象
```

### 实现边界

- 只能拦截插件签名声明的接口和方法，不能把插件当作任意 AOP 切面。
- SQL 改写必须处理参数映射、别名、子查询、分页和方言差异。
- 多个插件按注册顺序形成嵌套代理，分页、数据权限、审计插件需要明确顺序。
- 插件应尽量保持幂等，避免同一 SQL 被重复追加条件。

## Q2：如何用 MyBatis 插件实现低侵入数据权限？

**一句话结论：** 由业务上下文提供租户或数据范围，插件只负责在明确的 SQL 边界追加安全条件，并通过白名单、参数化和审计避免把权限逻辑变成不可控的 SQL 拼接。

### 推荐链路

1. 登录上下文解析用户、租户和数据范围。
2. 通过线程上下文或显式调用参数传递只读的权限快照。
3. 插件识别需要做数据隔离的 Mapper/方法白名单。
4. 解析或包装原 SQL，追加参数化的 `tenant_id`、组织范围或授权表条件。
5. 绑定新增参数并执行原有查询。
6. 记录命中的规则、SQL 模板标识和拒绝原因，便于审计。

### 安全边界

- 不允许把用户输入直接拼接进 `${}` 或权限 SQL。
- 对更新、删除和批量 SQL 必须单独验证，不能只保护查询。
- 超级管理员、跨租户任务和数据导出应显式声明权限模式，不能依赖默认绕过。
- 解析失败时默认拒绝或转人工处理，不能静默放行全量数据。

### 面试追问

- Q：为什么不在每个业务 SQL 中手写权限条件？
  A：手写容易遗漏且难统一审计；插件能降低侵入，但必须限制适用范围并保留显式例外。
- Q：权限条件放在 SQL 哪一层？
  A：优先在业务明确的查询边界或授权视图中处理；复杂 SQL 统一改写时要验证 JOIN、子查询和分页语义。
